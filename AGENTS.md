# Telegram Cloud Core / TGFS

Этот репозиторий — источник истины для архитектуры и задач TGFS.

## Работа с контекстом

1. В новой сессии сначала читать `docs/STATE.md` и `docs/KANBAN.md`.
2. Затем читать документ, ADR и Issue только по текущей теме. Проверять актуальный head перед записью.
3. Документация на русском, идентификаторы и примеры API на английском.
4. Отличать исходные требования, проверенные факты, предложения и принятые решения. Не переводить ADR в accepted без явного согласования.
5. Пока пользователь не изменит этап, заниматься документацией и канбаном; не начинать реализацию.

## Малые обновления

- Один существенный вопрос — одна Issue; проверять существующие задачи перед созданием новой.
- Менять только затронутые разделы. Обновлять STATE: результат, открытый вопрос, следующий шаг.
- Менять статус карточки в KANBAN при изменении фактического состояния; закрытие Issue означает выполненные критерии, а не просто наличие черновика.
- ADR имеют статусы proposed / accepted / superseded / rejected. Заменённое решение сохранять со ссылкой на новое.
- Проверять ограничения Telegram по официальным источникам и указывать дату; экспериментальные результаты не выдумывать.
- Не помещать токены, proxy-пароли и пользовательские сессии в Git, Issues или mount options.
- При работе с деревом Git сохранять существующие файлы, включая LICENSE; не использовать force push для документационных изменений.

Подготовленный текст, вопрос или план сам по себе не означает, что пользователь принял предложенную архитектуру.
