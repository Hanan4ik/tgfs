# Исходные требования и первичная оценка

Статус: изложение запроса пользователя и предлагаемых поправок; не финальная спецификация.

## Что сохраняем из исходной идеи

- Канал, подготовленный в формате TGFS, можно монтировать на Linux.
- Изоляция конфигураций разных каналов и ботов; системная директория `/etc/tgfs`.
- Токен BotFather, выбор прокси при первоначальной настройке; поддержка собственного Bot API endpoint.
- Основной канал и при необходимости служебный канал для пересылок; автоматическая очистка служебных сообщений по настройке.
- Явная инициализация канала: отправить ACK, получить ID, заменить на служебную запись, закрепить.
- Данные всегда загружать как document; большие файлы разбивать; проверять размер и SHA-256.
- Предусмотреть каталоги, обычные файлы, перспективу ссылок.
- Обсудить ограничения Bot API и возможность TDLib до разработки.

## Оценка предложенного решения

| Исходная идея | Что нужно уточнить или изменить |
| --- | --- |
| Похоже на NFS | Похож способ использования. Для первой реализации достаточно FUSE; NFS-протокол не требуется. |
| Новый тип tgfs-channel2 для каждого конфига | Один mount helper и выбор профиля через source/option проще упаковки и сопровождения. |
| ACK: start_id;last_used_id | Полезная точка входа; для восстановления нужны magic, версия формата, fs_uuid и указатель на завершённый каталог. Последний отправленный ID не равен последнему commit. |
| Пин всегда позволяет прочитать ACK | Нужно учитывать другой закреплённый пост, снятие закрепления и явный резервный ID superblock. |
| Поиск имени во всём канале | Для обычных операций нужен локальный индекс, восстанавливаемый из удалённого каталога. Bot API не даёт обычного поиска истории. |
| Чтение через null-канал | Рабочий кандидат для получения Message по известному ID; дорого для каждого read. Обычный путь — уже сохранённый file_id. |
| Лимит отправки 50 MB определяет chunk | Для cloud надо учитывать также скачивание 20 MB. Кандидат — 16 MiB в обе стороны. |
| Свой endpoint означает части почти 2 GB | Возможности нужно проверять; большой максимальный upload не обязывает выбирать максимальный chunk. |
| hash+size идентифицирует файл | Это признак содержимого; inode и версия нужны отдельно. Два независимых пустых файла имеют одинаковые hash+size. |
| size решает коллизию hash | Не исключает одинаковый размер у коллизии. SHA-256 даёт практическую проверку целостности, не математическую гарантию уникальности. |
| Последняя цифра имени показывает окончание | Упорядоченный список частей и их количество должны быть в каталоге; суффиксы служат только для человека. |
| Собирать до совпадения хеша | Сначала известно точное число частей, их размеры и порядок; затем проверяется результат. Не нужен перебор комбинаций. |
| Изменять last_used_id после каждого upload | Для видимости версии нужен отдельный шаг commit; обрыв посередине не должен публиковать полфайла. |

## Исправление разбиения

В исходном псевдокоде при размере `C+1` цикл отправит `C` байт, но условие `last_i == 0` пропустит остаток. Имена также начинаются с `.2` при `i=1` и `i+1`.

Эскиз алгоритма, не реализация:

```text
part_index = 0
while true:
    data = read_up_to(C)
    if data is empty: break
    upload_document(data, part_index)
    part_index += 1
assert uploaded_bytes == file_size
publish_completed_version()
```

При пустом файле частей нет, есть запись inode с размером 0. При точном кратном C лишний пустой document не отправляется. Необходимые граничные случаи: `0, C-1, C, C+1, 2C, 2C+1`.

## Границы

Проект ориентирован на хранение файлов, а не на низкую задержку диска, общую сетевую POSIX-блокировку или запуск БД поверх mount. Импорт произвольных сообщений, несколько одновременно пишущих хостов и полная POSIX-совместимость требуют отдельных решений. Исходные требования не заменяются этими предложениями автоматически.
