# Первый этап реализации: ядро чтения на C

Дата: 2026-11-14. Пользователь разрешил переход от проектирования к реализации.

## Что работает

`tgfs --snapshot DIR ls /path` разрешает путь через DIRECTORY с записями
`name + object_id` и выводит имена непосредственных детей.
`tgfs --snapshot DIR cat /path` выбирает FILE_COMMIT, получает точные refs
частей и выдаёт байты в stdout. Проверяет метаданные и SHA-256 каждой части
до выдачи её байтов, затем SHA-256 целого файла. Пустой файл возвращает EOF.

Реализовано правило A/110, B/120, повтор A/130: остаётся B/120. Для одной
operation_id используется первое корректное сообщение по исходному ID;
различные содержательные поля одного operation_id отвергаются. Изменение
next_message не создаёт новую операцию. Входной порядок записей не важен.

Это CLI и библиотечный интерфейс чтения, а не смонтированная файловая система.
Snapshot ls/cat не обращаются к Telegram. Отдельно реализованы [Bot API транспорт и probe](BOT_API_TRANSPORT.md). Добавлен [сбор журнала и индекс записей](CHANNEL_SCAN.md). Удалённое чтение подключено через [read](REMOTE_READ.md). SQLite-индекс и кэш добавлены в [read](PERSISTENT_CACHE.md); новый файл публикуется через put. FUSE пока отсутствует. Для snapshot токен не нужен.

## Сборка и запуск

Зависимости: компилятор C11, Make, заголовки/библиотека OpenSSL libcrypto, libcurl >= 7.85, SQLite >= 3.31.
Для тестов нужен Python 3 из стандартной библиотеки.

Debian/Ubuntu: `sudo apt-get install build-essential libssl-dev libcurl4-openssl-dev libsqlite3-dev python3`.
Arch Linux: `sudo pacman -S --needed base-devel openssl curl sqlite python`.

```sh
make
./build/tgfs --snapshot examples/hello ls /
./build/tgfs --snapshot examples/hello ls /documents
./build/tgfs --snapshot examples/hello cat /documents/hello.txt
make test
make sanitize
```

Последний cat выводит `hello` и перевод строки. Все команды запускаются
из корня репозитория. Код возврата: 0 — успех, 1 — ошибка операции,
2 — неверные аргументы. Диагностика идёт в stderr, данные — в stdout.

## Локальный snapshot adapter

`snapshot.json` — формат тестового адаптера, **не новый Telegram wire-format**.
В нём находятся:

| Поле | Смысл |
| --- | --- |
| superblock | JSON SUPERBLOCK из текущей документации |
| root_entries | Явно заданный для теста список имён и object_id корня |
| messages | Массив известных сообщений одного тома |
| messages[].message_id | Положительная десятичная строка исходного ID |
| messages[].caption | JSON CHUNK, DIRECTORY или FILE_COMMIT |
| messages[].document | Имя локального файла с байтами соответствующего document |
| messages[].filename | Имя Telegram document для CHUNK, например hello.txt.0 |

Пример целиком находится в [examples/hello](../examples/hello/snapshot.json).
Метаданные DIRECTORY/FILE_COMMIT — JSON в отдельных documents. Байты CHUNK
загружаются только при cat: ls не скачивает и не проверяет содержимое файлов.
CLI не предполагает, что snapshot является проверенным экспортом канала:
полнота, источник и свежесть снимка должны быть установлены будущим backend.

root_entries задаётся явно, чтобы не выбирать за пользователя parent_id
корневого DIRECTORY и правила его публикации. Два сообщения DIRECTORY одного
объекта дают ошибку неоднозначности при обращении к этому каталогу. Прототип
не выбирает последнее сообщение самовольно. Публикация DIRECTORY и его
синхронизация остаются открытыми в #2.

## Границы и ограничения

- Поддерживается выбранная для примеров оболочка FILE_COMMIT:
  общие поля в caption, parts в JSON document. Это адаптер существующего
  примера, а не утверждение всех оставшихся вариантов протокола.
- UUIDv4 для version_id/operation_id используется согласно примерам;
  генерация новых ID пока отсутствует.
- Метаданные ограничены 8 MiB на JSON, 64 уровнями вложенности и 65 536
  записями/частями/entries. Это локальные лимиты прототипа. Байт одной части
  максимум 20 971 520. Имена — до 255 байт, путь — до 4096 байт.
- Индекс пока в памяти: поиск части по ID — бинарный; выбор объектов и
  проверка повторов/имён используют линейные и квадратичные обходы. Это
  ограничивает масштаб тестового снимка; массовый импорт требует другого индекса.
- Только абсолютные пути; `.`/`..`, symlink и изменения файловой системы
  отсутствуют. При отсутствии опубликованной версии cat завершается ошибкой.
- Snapshot documents читаются относительно открытого каталога. Пути с `/`,
  переходы `..`, symlink и специальные файлы не используются как documents.
- Ошибка более поздней части или общего хеша может оставить проверенный
  префикс в stdout. Код возврата нужно проверять; полное чтение не является
  атомарным буферизованным скачиванием. Детальный recovery остаётся в #10.

## Модули и проверки

| Файл | Ответственность |
| --- | --- |
| include/tgfs/tgfs.h | Интерфейс открытия снимка, перечисления и чтения |
| src/main.c | Аргументы CLI и вывод |
| src/core.c | Индекс, разрешение пути, выбор commit, refs и чтение частей |
| src/json.c | Безопасное чтение локальных documents и разбор значений JSON |
| third_party/cjson | Зафиксированный cJSON 1.7.19 с исходной MIT-лицензией |
| tests/integration.py | Сквозные проверки запуска с временными снимками |

Для первого этапа выбраны cJSON и OpenSSL: cJSON включён в дерево с точной
версией и лицензией, SHA-256 считается через EVP. Для HTTP теперь используется libcurl; Для производного индекса/кэша используется SQLite; FUSE ещё не подключён. LICENSE TGFS сохранён без изменений.

Проверяются несколько частей, UTF-8 имена, пустые файлы/каталоги,
незавершённая загрузка, конфликт повторов, повреждения размера/хеша,
несовпадение версии/родителя/backlink, неоднозначный DIRECTORY и некорректный
JSON/диапазоны. CI запускает сборку, тесты, ASan и UBSan.

Локально LeakSanitizer не работает в среде под ptrace. Поэтому ASan/UBSan
проверяются с `ASAN_OPTIONS=detect_leaks=0`; в CI этот обход не включён.
Это ограничение проверки утечек, а не доказательство их отсутствия.
