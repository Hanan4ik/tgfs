# Состояние проекта

Обновлено: 2026-11-03, Europe/Moscow. Этап: документация и канбан.

## Подтверждено пользователем

- Проект `Hanan4ik/tgfs`: Linux mount для Telegram-канала в формате файловой системы.
- Нужны чтение и в дальнейшем запись файлов с разбиением на части и проверкой целостности.
- Нужны несколько конфигураций, настройка бота/канала и обсуждение Bot API против TDLib.
- Для первого прототипа выбран публичный облачный Bot API (api.telegram.org), без собственного Bot API server. TDLib отложен. ADR-0001 accepted.
- Язык реализации — C. Библиотеки HTTP/JSON, хеширования и FUSE ещё не выбраны; программирование пока не начато.
- Повторные загрузки одного содержимого могут оставлять несколько комплектов частей. Чтению достаточно первого полного комплекта с верным общим SHA-256 и размером. Дубликаты нежелательны; требуется механизм очистки (#9), алгоритм пока открыт.
- Принят журнал без координатора: постоянный заголовок channel_id/start_id, граница по фактическому ID отправленного маркера, независимое восстановление локального индекса. ADR-0003 accepted, ADR-0002 superseded.
- next_message обязателен во всех сообщениях TGFS (ID либо null); нужен для ускорения обхода на фоне роста числа служебных сообщений/ID. При разрыве или непроверенном интервале — сканирование до маркера; отсутствие ссылки не доказывает конец.
- Принят общий постоянный object_id объекта TGFS в удалённых метаданных: сохраняется при переименовании и изменении содержимого, восстанавливается одинаковым на всех машинах. Локальные inode/FUSE nodeid назначаются независимо. Выбран UUIDv4 из криптографически стойкой случайности; в JSON — строка нижнего регистра с дефисами, сохраняемая до первой отправки.
- Принят отдельный FILE_COMMIT как сигнал завершённой публикации версии после отправки всех частей; нужны точные refs всего комплекта через commit/манифест. Wire-format и гарантии fsync ещё согласуются.
- Для одного object_id принята последняя опубликованная версия по ID исходного FILE_COMMIT: устаревшая основа не блокирует замену и не создаёт конфликтную копию. Старые записи автоматически не удаляются; rename/delete ещё открыты.
- Принята идемпотентность публикаций: operation_id устойчиво сохраняется до первой отправки и повторно используется при retry; учитывается первый корректный commit операции по минимальному ID. Повторы не повышают приоритет; next_message исключён из сравнения содержательных полей. Несовпадение этих полей под одним ID — ошибка протокола. Генерация ID и точное сравнение ещё согласуются.
- Принята архитектура каталогов/имён: каталог — объект со своим object_id; связь parent_object_id + name -> object_id отделена от содержимого. Пустые каталоги имеют удалённые метаданные и восстанавливаются без локального индекса; фиктивные data documents не нужны. Точные записи создания/публикации ещё обсуждаются.
- Сводный SUPERBLOCK: JSON-текст в закреплённом сообщении; magic, format_version, type, start_id, root_object_id (UUIDv4), next_message. channel_id берётся из локальной конфигурации. Заголовок объявляет корень. Примеры локального размещения и индекса: SUPERBLOCK_V1.md; формат остальных типов ещё обсуждается.
- Принято сохранение part_sha256 для проверки отдельных частей. Пустой файл — текстовый FILE_COMMIT без document/CHUNK и без байтов-заглушек: метаданные читаются из Message.text; у CHUNK — из Message.caption. Точный JSON commit/манифеста ещё обсуждается.
- Записана рассмотренная схема отправки 60 MiB: три части по 20971520 и текстовый FILE_COMMIT со встроенным parts — FILE_COMMIT_V1.md. Общие object_id/version_id читаются второй машиной без регенерации; локальные inode могут различаться. Это не закрывает первые имена/каталоги, большие манифесты, генераторы ID, parser limits или эксперименты. Номер части берётся из последнего суффикса document.file_name вида video.mp4.0; part_index в caption отсутствует.
- Принят обязательный parent_id в caption CHUNK: UUIDv4 object_id родительской директории, для корня root_object_id. Цель должна иметь тип directory, а не файл или symlink. Все части комплекта содержат одинаковый parent_id; он сохраняется в локальном индексе. Публикация первого имени/пустого файла и правила rename/move/hardlink ещё требуют отдельного решения.
- Принята обратная ссылка из CHUNK на FILE_COMMIT. Рабочее поле file_commit_id: строка исходного ID либо null до публикации; после commit captions выбранных частей дополняются каноническим ID операции. Это восстанавливаемая служебная ссылка, не новая точка публикации и не доказательство отсутствия commit при null. Переиспользование/очистка требуют проверки refs.
- После MVP regular/directory нужно реализовать symlink, hardlink и специальные биты прав (sticky/setuid/setgid); принято требование предусмотреть это в архитектуре. План POSIX_METADATA_PLAN.md: тип объекта, несколько entries на один object_id, target_path ссылки и метаданные отдельно от bytes. Точные поля, UID/GID-политика и исполнение прав ещё proposed.
- Сейчас проектируем вместе, программирование не начинаем.

## Что выяснено

В исходном репозитории был только LICENSE. Проверены официальные источники Telegram и Linux; опубликованы черновики и девять Issues. Живых экспериментов с Telegram или FUSE не проводилось. Выбран C; конкретные библиотеки ещё не выбраны. ADR-0001 и ADR-0003 accepted; ADR-0002 superseded. Принятие ADR-0003 не означает готовый wire-format или экспериментальную проверку. Issue #1 закрыта как решение о транспорте; непроверенные предположения остаются в #6.

Главные поправки: учитывать предел скачивания Bot API, хранить индекс вместо поиска по имени в канале, отделить завершённую версию от частичных загрузок, не считать SHA-256 идентификатором inode.

Сверка Issues 2026-11-03: проверены #1–#9. #1 остаётся закрытой; #2–#9 открыты. Отмечены принятые принципы FILE_COMMIT, refs частей, object_id и чтения дубликатов; конкретные алгоритмы, эксперименты и реализация остаются незавершёнными. Устаревшие задачи смены superblock и fs_uuid приведены к текущей схеме.

Каталог незавершённых сценариев сбоев: [UNRESOLVED_FAILURE_SCENARIOS.md](UNRESOLVED_FAILURE_SCENARIOS.md), 51 сценарий F01–F51. Разделены отсутствие решения, идея, очевидное действие и принятое правило без проверки. Каталог не меняет принятые решения и не закрывает Issues; при завершении сценария нужно обновлять его статус и связанную задачу.

## Следующий вопрос

Фокус #2 совместно с #3: object_id и необходимость FILE_COMMIT приняты; для содержимого одного объекта принята последняя опубликованная версия. Правило повторов operation_id также принято. Следующий конкретный вопрос — первое создание имени файла (parent_object_id + name) одновременно с первой публикацией. Затем уточнить формат v0.1 на основе PROTOCOL.md: черновик [CHUNK_V1.md](CHUNK_V1.md), манифест, FILE_COMMIT, идентификаторы операций/версий и записи создания каталогов/публикации имён. Заголовок собран в [SUPERBLOCK_V1.md](SUPERBLOCK_V1.md). Модель parent_object_id + name -> object_id принята. В рассмотренном примере используется часть 20971520 байт (20 MiB); граничный эксперимент не проводился. Генератор/кодирование version_id уточняется отдельно. Записан черновик CHUNK с JSON caption и предложением UUIDv4 для версии. Очистка старых версий возможна только после публикации новой и проверки безопасности; ограничения Bot API сохраняются. Генерация ID, сравнение содержательных полей и fsync в принятой журнальной схеме. В #6/#7 запланировать маркеры, разрывы/гонки next_message, проверку непроверенных промежутков и стоимость долгого использования. Старая версия [сценария hello.txt](CREATE_FILE_SCENARIO.md) помечена исторической. Доверенный удалённый checkpoint и свежее обнаружение для экземпляра без права отправки остаются открытыми.

## Как продолжить без нового большого плана

Достаточно запроса «продолжаем tgfs, вопрос #1» или «уточним формат частей». Прочитать этот файл, нужную Issue и связанный документ; внести небольшой согласованный diff; обновить здесь только изменившееся состояние. Не повторять весь проект в каждом ответе.
