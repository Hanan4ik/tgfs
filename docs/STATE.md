# Состояние проекта

Обновлено: 2026-11-03, Europe/Moscow. Этап: документация и канбан.

## Подтверждено пользователем

- Проект `Hanan4ik/tgfs`: Linux mount для Telegram-канала в формате файловой системы.
- Нужны чтение и в дальнейшем запись файлов с разбиением на части и проверкой целостности.
- Нужны несколько конфигураций, настройка бота/канала и обсуждение Bot API против TDLib.
- Для первой версии выбран Bot API ради простоты реализации; TDLib отложен. ADR-0001 accepted.
- Повторные загрузки одного содержимого могут оставлять несколько комплектов частей. Чтению достаточно первого полного комплекта с верным общим SHA-256 и размером. Дубликаты нежелательны; требуется механизм очистки (#9), алгоритм пока открыт.
- Принят журнал без координатора: постоянный заголовок channel_id/start_id, граница по фактическому ID отправленного маркера, независимое восстановление локального индекса. ADR-0003 accepted, ADR-0002 superseded.
- next_message обязателен во всех сообщениях TGFS (ID либо null); нужен для ускорения обхода на фоне роста числа служебных сообщений/ID. При разрыве или непроверенном интервале — сканирование до маркера; отсутствие ссылки не доказывает конец.
- Принят общий постоянный object_id объекта TGFS в удалённых метаданных: сохраняется при переименовании и изменении содержимого, восстанавливается одинаковым на всех машинах. Локальные inode/FUSE nodeid назначаются независимо; генерация/кодирование object_id ещё согласуются.
- Сейчас проектируем вместе, программирование не начинаем.

## Что выяснено

В исходном репозитории был только LICENSE. Проверены официальные источники Telegram и Linux; опубликованы черновики и девять Issues. Живых экспериментов с Telegram или FUSE не проводилось. Язык реализации и библиотека не выбраны. ADR-0001 и ADR-0003 accepted; ADR-0002 superseded. Принятие ADR-0003 не означает готовый wire-format или экспериментальную проверку. Issue #1 закрыта как решение о транспорте; непроверенные предположения остаются в #6.

Главные поправки: учитывать предел скачивания Bot API, хранить индекс вместо поиска по имени в канале, отделить завершённую версию от частичных загрузок, не считать SHA-256 идентификатором inode.

## Следующий вопрос

Фокус #2 совместно с #3: object_id принят; далее уточнить FILE_COMMIT, идемпотентность, конфликт одного пути и fsync в принятой журнальной схеме. В #6/#7 запланировать маркеры, разрывы/гонки next_message, проверку непроверенных промежутков и стоимость долгого использования. Старая версия [сценария hello.txt](CREATE_FILE_SCENARIO.md) помечена исторической. Доверенный удалённый checkpoint и свежее обнаружение для экземпляра без права отправки остаются открытыми.

## Как продолжить без нового большого плана

Достаточно запроса «продолжаем tgfs, вопрос #1» или «уточним формат частей». Прочитать этот файл, нужную Issue и связанный документ; внести небольшой согласованный diff; обновить здесь только изменившееся состояние. Не повторять весь проект в каждом ответе.
