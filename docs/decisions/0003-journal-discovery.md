# ADR-0003: журнал без координатора, маркер границы и next_message

- Статус: **accepted** — принцип согласован пользователем 2026-11-03; wire-format и реализация не утверждены.
- Дата: 2026-11-03
- Обсуждение: [#2](https://github.com/Hanan4ik/tgfs/issues/2); проверки [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7).
- Заменяет предложение [ADR-0002](0002-catalog.md) о публикации полного каталога сменой общего указателя.

## Причина

Центрального координатора нет. Каждый экземпляр TGFS должен самостоятельно обнаруживать записи других машин и восстанавливаться после их падения. Проверка перед редактированием закрепа, reserved_by и ожидание очереди не дают атомарного compare-and-swap. Редактируемая верхняя граница не должна быть единственным способом обнаружения данных.

## Решение

1. Закреп — постоянная точка входа: magic, format_version, channel_id, start_id. Идентичность тома задаёт channel_id; отдельный случайный fs_uuid не нужен. start_id — фактический ID сообщения инициализации, а не константа 2 или 3. Его также сохраняют в профиле на случай чужого закрепления.
2. Части и записи публикации добавляются независимо. Общий каталог не перезаписывается целиком каждой машиной. Локальный индекс восстанавливается из журнала; он не является единственной копией метаданных.
3. Для новой границы экземпляр отправляет обычное служебное сообщение SCAN_MARKER в исходный канал. Из ответа sendMessage берётся result.message_id = B. Диапазон до B включительно конечен; последующие сообщения относятся к следующей синхронизации. Нельзя предсказывать ID.
4. Для чтения известных ID применяется forwardMessage в отдельный служебный чат. result.message_id принадлежит копии; при forward_origin.type=channel поля forward_origin.chat.id и forward_origin.message_id обозначают оригинал. Сохраняется также исходный ID запроса; происхождение проверяется, а не выводится из ID копии.
5. Каждый экземпляр хранит свой индекс, проверенные интервалы и позицию полного сканирования. Падение другого отправителя не требует ожидания или захвата его блокировки.

Этот механизм устраняет зависимость обнаружения от гонки обновления общей границы. Он не является распределённой блокировкой, транзакцией нескольких файлов или готовой гарантией POSIX при конкурентной записи.

## Обязательный next_message

Поле next_message обязательно во всех сообщениях TGFS: в заголовке, маркерах, commit, а для документов — в служебной оболочке caption. Значение — ID следующего сообщения TGFS того же канала (десятичная строка) либо null, если продолжение пока неизвестно. Отсутствующее поле — несоответствие новому формату; для старых записей нужен явный режим совместимости.

Иллюстрация оболочки, не окончательный wire-format:

```json
{"magic":"TGFS","format_version":1,"channel_id":"-1001234567890","type":"SCAN_MARKER","next_message":null}
```

После отправки нового сообщения экземпляр ищет ближайшее предыдущее сообщение TGFS по меньшим ID, используя проверенный локальный индекс или обратный поиск. Посторонние сообщения не изменяются. Предшественнику записывается next_message с фактическим ID нового сообщения. Если обнаружены промежуточные TGFS-записи, восстанавливаются соседние связи по возрастанию ID.

Байты документов и смысл опубликованной операции остаются неизменяемыми; next_message — изменяемая навигационная метаинформация. При редактировании нужно сохранять остальные поля, а целостность содержимого проверять независимо от навигационной оболочки. Право редактировать сообщения другого writer, в том числе при разных ботах, проверяется в #6; без него восстановление ссылок может быть недоступно, но сканирование остаётся возможным.

При гонке или падении ссылка может отсутствовать, устареть либо перескочить через запись. Поэтому:

- next_message должен вести вперёд в том же канале; цель проверяется на magic и принадлежность тому.
- null не доказывает конец канала. Источник границы — отправленный маркер.
- Необследованный промежуток нельзя объявить проверенным лишь потому, что ссылка его перескочила: возможна затёртая конкурентным редактированием связь.
- При разрыве, неподходящей цели или непроверенном промежутке выполняется сканирование соответствующего диапазона до B. Сетевые ошибки и 429 не превращаются в отсутствующие сообщения; недоступная запись может означать ошибку доступа, а не пустоту.
- Найденные связи восстанавливаются по возможности; корректность восстановления данных не зависит от успешности такого редактирования.

## Стоимость длительного использования

Маркеры создают дополнительные сообщения и занимают ID. Удаление маркера не делает его ID повторно доступным; при длительной работе накапливаются большие диапазоны, в том числе пропуски и посторонние записи. Полный перебор каждого ID при каждой синхронизации может стать очень долгим.

Поэтому next_message — обязательный элемент структуры и основной навигационный путь по известной проверенной цепочке. Его дополняет локальный индекс: уже проверенные интервалы повторно не сканируются без причины. На чистой машине или после повреждения цепочки худший случай остаётся линейным по диапазону ID; одна ссылка не гарантирует быстрого безопасного обхода при гонках. Формат удалённых проверенных checkpoint/индексов для ускорения такого восстановления ещё предстоит согласовать. Удалять старые маркеры, на которые есть ссылки, без их перенаправления нельзя.

## Публикация файла

Уточнение, согласованное пользователем 2026-11-03: после всех частей отправлять отдельный FILE_COMMIT с operation_id, идентичностью/именем файла, размером, общим SHA-256 и точными refs частей или манифеста. Части без commit не публикуют файл. После commit не требуется менять закреп. Локальный intent помогает разобрать потерянный ответ; повторная отправка не считается автоматически исключённой API.

Приняты необходимость commit и требование точных ссылок на части; окончательное размещение списка в commit/манифесте и его кодирование ещё согласуются. Общий object_id принят отдельно (см. PROTOCOL.md).

Уточнение, принятое пользователем 2026-11-03: среди разных публикаций содержимого одного object_id показывать последнюю по message_id исходного FILE_COMMIT. Публикация на основе старой версии — обычная замена, без обязательного base_version_id, блокировки конфликта или автоматического слияния. Старая история не удаляется самим выбором новой версии. Подробности и границы: раздел «Последняя опубликованная версия» в PROTOCOL.md.

Уточнение, принятое пользователем 2026-11-03: operation_id создаётся и устойчиво сохраняется до первой отправки commit; повторы одного логического сохранения используют тот же ID и одинаковое содержательное описание. Учитывается первое корректное сообщение операции (минимальный исходный message_id); последующие повторы не создают новую версию и не повышают её приоритет. Среди разных операций побеждает максимальный ID их первых корректных commit. next_message не участвует в сравнении содержимого повторов. Несовпадающие содержательные поля под одним operation_id — ошибка протокола. Подробности и пример 120/125/130 — в PROTOCOL.md.

Точные поля commit, генерация/кодирование operation_id и version_id, сравнение содержательных полей, восстановление при повреждении журнала, создание разных объектов по одному пути и rename/delete остаются открытыми. Принятие этого правила не означает, что решены все конфликты файловой системы.

## Проверки и ограничения

Живых экспериментов не проводилось. В #6 проверить маркер, порядок ID, пересылку исходных постов и чужих пересылок, пропуски и protected content, права и параллельные экземпляры. В #7 проверить падение после send до связывания, потерю ответа, затёртую/перескочившую ссылку, восстановление без SQLite и рост диапазона после множества маркеров. Сравнивать результат ускоренного обхода с полным сканированием одной границы B.

Свежая граница требует права отправки в исходный канал. Read-only экземпляр без него может использовать только известную границу; независимое обнаружение свежего конца для него пока не решено. Пересылки не направляются в исходный канал и не порождают бесконечный самосканируемый хвост.

Официальные источники проверены 2026-11-03:

- https://core.telegram.org/bots/api#sendmessage — отправка возвращает Message.
- https://core.telegram.org/api/updates#message-id-sequences — возрастающая общая для участников последовательность ID канала.
- https://core.telegram.org/bots/api#forwardmessage и https://core.telegram.org/bots/api#messageoriginchannel — результат пересылки и происхождение.
- https://core.telegram.org/bots/api#editmessagetext и https://core.telegram.org/bots/api#editmessagecaption — редактирование навигационной оболочки; серверного условия CAS здесь нет.

Схема границы и обязательность next_message — принятые архитектурные решения проекта на основе этих свойств API, а не обещание Telegram о готовом протоколе TGFS.
