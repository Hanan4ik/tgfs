# Восстановление публикации имени

Реализован явный `tgfs intent --resume-directory` для создания нового файла
и публикации DIRECTORY в `mkdir`.
Это продолжение публикации имени, не полное resume. Режим не отправляет новые
CHUNK/FILE_COMMIT, не заменяет файл и не восстанавливает удалённые имена.
С --repair-backlinks одновременно использовать нельзя: необходимые backlinks
режим проверяет/исправляет сам.

## Условия и запреты

Для put требуются intent kind=put, replace=false, подтверждённый canonical FILE_COMMIT,
verified staging/CHUNK/refs и отсутствие ненаблюдённых/неоднозначных частей.
Сохраняются UUID объекта, версии, FILE_COMMIT и ADD из первоначального intent.

Если ADD уже найден в capture, возвращается directory_resume=already_observed
без новой публикации. Это исторический факт: после ADD мог быть REMOVE,
поэтому режим не пытается восстановить имя, отсутствующее в текущем дереве.

Для нового файла обычное продолжение доступно из фаз backlinks_pending,
commit_send_pending или commit_response_uncertain. По порядку оригинального
writer эти фазы предшествуют **первой попытке ADD**. Из directory_send_pending
повтор возможен, если журнал содержит pending и подтверждённый rejected для
исходного add_operation_id, а срок retry_after уже истёк. Для
directory_response_uncertain, published_navigation_pending и complete отсутствие
ADD не разрешает retry: исход мог быть неизвестен или имя уже удалили.
Не редактируйте phase вручную для обхода проверки.

Дополнительно проверяется backlink-repair.log. Любая прежняя запись
с event=directory_send_pending блокирует повтор, пока новый capture не
подтвердит ADD либо writer или recovery не сохранит подтверждённый отказ
именно этой попытки (правила ниже). Повреждённый/слишком большой лог также
блокирует действие. Журнал не очищается автоматически. Ненайденный ADD сам по себе не доказывает, что
отправка не состоялась.

## Порядок выполнения

1. Берётся та же локальная flock, что у ремонта backlinks. Создание log-файла
   закрепляется fsync каталога. Намерение и staging не переписываются.
2. Проверяются существующий родительский путь, его UUID и свободное имя в
   выбранном capture. Сохранённые DIRECTORY caption/ADD сверяются с этими
   UUID, именем и исходным add_operation_id. Публикуется только этот документ.
3. Исправляются необходимые backlinks существующих CHUNK по прежнему протоколу.
   Перед записью используется свежая проверка сообщений через служебный канал.
4. FILE_COMMIT перечитывается; неизменяемые поля/document сверяются с capture.
   Перед ADD повторно проверяется закреп SUPERBLOCK.
5. До sendDocument журнал получает directory_send_pending с UUID операции ADD;
   запись завершается fsync. После этого отправляется один directory.json.
6. Проверяются возвращённые канал/ID/caption/filename/size. Подтверждённый ID
   записывается в log как directory_publication_confirmed с fsync.

При потере ответа pending остаётся: повтор со старым capture блокируется.
После нового scan совпавший ADD распознаётся как already_observed. Если ADD
не найден, слепого повторения не будет. Новый capture может иметь пропуски или
заканчиваться раньше выполнения запроса.

Проверка свободного имени относится к выбранному capture, а не даёт глобальную
блокировку канала. Параллельное независимое добавление после его маркера всё
ещё может привести к принятому конфликту имён. flock локальная; две копии
intent на разных машинах не координируются. Повторы одной ADD с тем же UUID
дедуплицируются читателем, но не устраняют лишние физические сообщения.

## Отчёт и оставшиеся этапы

При уже наблюдённой ADD: directory_resume=already_observed, resumed=false.
При новой подтверждённой отправке: directory_resume=published, resumed=true,
scope=capture_plus_recovery_response, publication=confirmed, новый ID в
directory_ids и next_step=capture_after_directory_publication.

local_phase остаётся исходной. Режим не объявляет весь intent завершённым,
не ремонтирует FILE_COMMIT.next_message на новый DIRECTORY и не изменяет
intent.json. Для подтверждения нового дерева/навигации нужен следующий scan.
can_resume остаётся false — это не универсальный сигнал готовности загрузки.
Ошибка после принятой публикации/сохранения ответа не означает откат ADD.

## Безопасный живой тест

Пользователь подтвердил предыдущий no-op ремонта commit41/CHUNK40. Для этого
режима нужен **intent создания**, а не replace:

```bash
git pull --ff-only
make
./build/tgfs intent "${tgfs_net[@]}" \
  --state-dir "$HOME/.local/state/tgfs/put-documents-hello-001" \
  --capture ./capture-010 \
  --resume-directory
```

Ожидается directory_resume=already_observed и resumed=false. ADD первоначального
создания есть в журнале, хотя имя позже удалили. Файл не должен появиться снова:
ls /documents на capture-010 по-прежнему пустой. Новый scan не нужен.
Не меняйте phase и не создавайте искусственный сбой для непустого resume.

116 тестовых методов; новые сценарии проверяют продолжение после неуспешных
backlinks, пустой файл, lost ADD response, явный reject и барьер повторной
отправки, конфликт имени и неизвестную фазу, повтор по новому capture и отсутствие
воскрешения после REMOVE. Проверяется сохранность intent и отсутствие новых
CHUNK/FILE_COMMIT. Локально 112 passed/4 kernel skips; ASan/UBSan с detect_leaks=0
из-за ptrace. Живое непустое продолжение ещё ожидает реального незавершённого
намерения. Загрузка недостающих частей добавлена в [RESUME_UPLOAD.md](RESUME_UPLOAD.md),
финализация — в [FINALIZE_METADATA.md](FINALIZE_METADATA.md) и
[FINALIZE_PUT.md](FINALIZE_PUT.md). Init/unlink resume и автоматический
cleanup log остаются открытыми.


## Прерванный mkdir (2026-11-18)

Для родительского ADD в `kind=mkdir` дочерний
DIRECTORY должен уже присутствовать в новом capture с точным сохранённым
пустым документом и metadata. Если ADD ещё не найден, требуется ровно один
дочерний документ; сохранённый child_message_id, если он есть, обязан совпадать.
Для mkdir не нужен data.bin.

Для mkdir фазы child_send_pending, child_response_uncertain и child_sent
предшествуют первой попытке ADD. В directory_send_pending продолжение возможно
только с парой pending/rejected для исходного UUID ADD и после срока ожидания.
Первоначальный mkdir держит общую с recovery блокировку до завершения. Если
дочерний документ отсутствует в capture, публикация родительского ADD блокируется.
Если исходная ADD уже наблюдалась, возвращается already_observed без отправки.

Если первая отправка дочернего DIRECTORY явно отклонена, writer сохраняет
child_send_rejected с UUID дочернего объекта. Когда истёк cooldown, тот же
`--resume-directory` с новым capture сверяет родителя, свободное имя, сохранённые
документы и pin. Он отправляет только дочерний DIRECTORY и возвращает
`child_resume=published` и `next_step=capture_after_child_publication`.
Следующий scan и повтор команды продолжают родительский ADD. При потере ответа
новый scan может подтвердить дочерний документ, а без этой находки повтор
блокируется. Старые intent без подтверждённого отказа сохраняют барьер.

Перед публикацией проверяются сохранённый path (включая вложенный каталог и
завершающий /), UUID родителя, свободное имя, исходный ADD UUID и caption.
Дочерний документ перечитывается через служебную копию, проверяются источник,
идентичность документа, metadata и next_message=null. Неожиданная ссылка,
изменённый pin, сбой чтения или очистки копии блокируют отправку. Дальше
используется тот же fsync-барьер и проверка ответа, что для put.

После published нужен новый scan и `--finalize`: он свяжет дочерний DIRECTORY
с подтверждённым ADD и атомарно завершит intent. Resume сам не редактирует
дочернюю навигацию и не переписывает intent.json. При неизвестном ответе
повтор по прежнему capture блокируется; новый capture с ADD даёт already_observed.

Безопасная проверка на уже завершённом пользовательском mkdir:

```sh
./build/tgfs intent "${tgfs_net[@]}" \
  --state-dir "$HOME/.local/state/tgfs/mkdir-documents-001" \
  --capture ./capture-011 --resume-directory
```

Ожидаются directory_resume=already_observed и resumed=false. Новые документы
не публикуются; искусственно прерывать mkdir не нужно. Непустой recovery
проверен тестовым API, живой прерванный mkdir пока не проверен.


## Повтор после подтверждённого отказа ADD (2026-11-18)

Новый запуск `--resume-directory` может повторить ADD, отклонённый **предыдущим
запуском этого режима**, сохраняя исходный документ и UUID. Внутри одного запуска
автоматических повторов и ожидания нет. Сначала исправьте причину ошибки;
при 429 дождитесь сохранённого retry_not_before и повторите ту же команду.

Барьер снимается только записью directory_send_rejected в том же приватном
журнале после разобранного ok=false, строкового description, совпадающих
HTTP/error_code в диапазоне 400–499 и отсутствующего result. Необязательные
parameters/retry_after должны иметь корректный формат. Для 429 обязательно
положительное retry_after; без него барьер остаётся. Запись содержит UUID ADD,
коды и абсолютный срок Unix time, записывается целиком и fsync до возврата ошибки.
Текст description, токен и сетевые адреса в журнал не попадают.

Повтор читает журнал под прежней flock. Rejected должен соответствовать одной
незавершённой pending-попытке той же операции. Чужой UUID, orphan/двойной rejected,
повреждённая строка либо подтверждённая публикация блокируют действие. После
окончания cooldown заново проверяются captured destination, fresh source и pin;
перед повтором создаётся новая pending-запись. Если этот повтор потеряет ответ,
старый rejected не снимает новый барьер. Ошибка сохранения rejected также не
разрешает повтор. Журнал и intent нельзя редактировать для обхода барьера.

5xx, несовпадающие HTTP/error_code, некорректный envelope/parameters, неизвестный
ответ, тайм-аут и неверный успешный Message не подтверждают отсутствие публикации.
Для них сохраняется прежнее правило: новый scan и сверка; отсутствие ADD в capture
само по себе не разрешает отправку. Старые журналы без rejected и исходные writer
intents в directory_response_uncertain не получают разрешение задним числом.
Повторы CHUNK/FILE_COMMIT, init/unlink этим изменением не реализованы.

Срок cooldown использует системные часы; при их переводе назад ожидание может
продлиться, часы должны быть корректными. Команда сообщает retry_after в ошибке,
а при раннем повторе — сохранённый срок retry_not_before. Проверки transport
теперь консервативно отмечают неполный/противоречивый отказ как outcome_unknown.

Основание: [Bot API: Making requests](https://core.telegram.org/bots/api#making-requests)
и [ResponseParameters](https://core.telegram.org/bots/api#responseparameters), проверено
2026-11-18: ok=false описывает неуспешный запрос, retry_after задаёт ожидание до
повтора. Строгое совпадение HTTP/error_code и сохранение барьера для 5xx — выбранная
консервативная политика прототипа, а не дополнительная гарантия Telegram.
