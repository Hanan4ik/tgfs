# Слияние изменений каталогов

Дата: 2026-11-15. Пользователь согласовал слияние независимых добавлений и
явные удаления. Ниже — реализованное кодирование первого прототипа на C;
это уточнение реализации принципа, а не готовые rename/move/транзакции.

## В канале

Тип записи остаётся DIRECTORY, метаданные — в caption, операции — в JSON
document. Каждое сообщение содержит один каталог. Для обычного каталога:

```json
{
  "magic": "TGFS",
  "format_version": 1,
  "type": "DIRECTORY",
  "object_id": "c5ccf4d2-79ba-4ab7-a4d0-d9b84b40a8cd",
  "parent_id": "a30d487f-167a-4eb3-8b06-b0676a039470",
  "next_message": null
}
```

Для корня object_id совпадает с root_object_id из SUPERBLOCK, parent_id=null.
SUPERBLOCK уже объявляет корень: без операций он пуст. Остальные каталоги
объявляются записью DIRECTORY, включая document с пустым operations.

Добавление имени:

```json
{
  "operations": [
    {
      "operation_id": "8bc3a88d-c494-4a04-9720-22577fabf032",
      "action": "ADD",
      "name": "notes.txt",
      "object_id": "d79c2b77-22b4-4f64-8bf5-748138dc2abe"
    }
  ]
}
```

Удаление этого добавления в следующем document того же каталога:

```json
{
  "operations": [
    {
      "operation_id": "80a66f96-38a9-4725-b3de-b8cf23ba017b",
      "action": "REMOVE",
      "name": "notes.txt",
      "observed_adds": ["8bc3a88d-c494-4a04-9720-22577fabf032"]
    }
  ]
}
```

| Поле | Правило |
| --- | --- |
| operation_id | UUIDv4 операции, устойчиво сохранённый writer до отправки |
| action | ADD или REMOVE |
| name | Имя записи каталога, правила имени ядра |
| ADD.object_id | UUIDv4 целевого файла/каталога |
| REMOVE.observed_adds | Непустой список UUID операций ADD, видимых удаляющей машине |

Один document может содержать несколько упорядоченных операций. Повторная
отправка сохраняет прежние operation_id и содержимое. Слияние локальное:
обнаружение второй версии не требует публиковать новый объединённый document.

## Применение

1. Сообщения сортируются по исходному message_id. Операции внутри document
   рассматриваются в порядке массива. ID служебных копий здесь не участвуют.
2. Для каждого operation_id учитывается первое появление. Повтор обязан иметь
   тот же каталог и тот же JSON операции; иначе ошибка. Повтор не повышает
   приоритет, не отменяет удаление, не меняет UUID объекта.
3. REMOVE подавляет только перечисленные ADD того же каталога и имени.
   Каждая ссылка должна разрешаться в предшествующий ADD: в более раннем
   исходном сообщении либо раньше в том же массиве. Ссылки на неизвестные,
   будущие, чужие имена/каталоги и REMOVE отвергаются. Дубликаты refs запрещены.
4. Оставшиеся ADD объединяются по имени. Несколько ADD одного имени с одним
   object_id дают одну запись. Если object_id разные — явная ошибка конфликта.
   Поздний REMOVE одного из конфликтующих ADD может устранить конфликт.
5. Порядок входных сообщений значения не имеет. Порядок вывода стабилен по
   первому оставшемуся ADD в исходном порядке; это не сортировка по алфавиту.

Таким образом независимые hello.txt, notes.txt, photo.jpg сохраняются вместе.
Повтор старого ADD после REMOVE не возвращает имя. Новое ADD с новым
operation_id после удаления снова создаёт имя. Одновременное добавление,
не включённое в observed_adds, сохраняется (семантика удаления увиденных
добавлений). Удаление не меняет FILE_COMMIT и не удаляет байты из Telegram.

Томбстоуны и исходные ADD нельзя просто выбросить: поздний повтор старого ADD
иначе восстановит удалённое имя. Checkpoint/GC этой истории ещё не реализованы.
Выбор победителя для одинакового имени разных объектов не согласован:
прототип сообщает ошибку, сохраняя все исходные записи.

## Совместимость и пределы

Старый document {entries:[...]} читается как один статический снимок. Несколько
таких снимков остаются неоднозначными; их отсутствие имени не является REMOVE.
Смешивать entries и operations в одном документе или для одного каталога
нельзя. Миграция требует явной публикации исходных имён как ADD; автоматической
генерации UUID на каждой читающей машине нет.

Старые snapshot root_entries поддерживаются как тестовый адаптер; непустой
root_entries нельзя смешивать с удалённым корневым DIRECTORY. Для нового
формата root_entries можно опустить. parent_id одного каталога должен быть
постоянным; move/rename этим кодом не утверждаются.

Восстановление пока реализовано в локальном ядре snapshot ls/cat, views в
памяти строятся при открытии. Конфликт/ошибка операции отклоняет весь снимок.
Сканер уже сохраняет DIRECTORY metadata, но не скачивает document: сетевой
импорт и writer операций предстоит подключить. Загрузка файла и ADD имени
пока не являются атомарной общей транзакцией. Содержимое файлов по-прежнему
выбирается через FILE_COMMIT. Лимит — 65536 уникальных операций на снимок,
65536 элементов в каждом массиве; обходы линейные/квадратичные, JSON до 8 MiB.

## Проверка

```sh
make
./build/tgfs --snapshot examples/directory-merge ls /
./build/tgfs --snapshot examples/directory-merge ls /documents
./build/tgfs --snapshot examples/directory-merge cat /documents/hello.txt
```

Во втором ls — hello.txt, notes.txt, photo.jpg; notes.txt и photo.jpg в этом
локальном примере пустые файлы. Пример содержит разные объекты файлов и
операции от независимых сообщений. Живой Telegram не изменяется.

13 новых тестов проверяют объединение/перестановку, cat после слияния,
повторы ADD/REMOVE, удаление увиденных добавлений, повторное создание,
конфликт имён и его устранение, неправильные refs/UUID/формат, корень и
неизменность родителя. Всего 61 тест, локальные ASan/UBSan с detect_leaks=0
из-за ptrace. Тест на нескольких живых writer ещё не выполнен.

## CLI unlink (2026-11-15)

[Writer удаления](UNLINK.md) публикует REMOVE для всех живых наблюдённых ADD
имени в выбранном capture; повторы и погашенные ADD исключаются тем же merge.
Ненаблюдённые ADD остаются. Это удаление имени, а не физический GC или rmdir.
