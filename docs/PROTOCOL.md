# Формат TGFS и восстановление

Статус: proposed, версия эскиза 0.1; не совместимый с реализацией wire-format. [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#5](https://github.com/Hanan4ik/tgfs/issues/5).

Подробный пример с полями и последовательностью сообщений: [создание hello.txt](CREATE_FILE_SCENARIO.md). Это конкретизация эскиза, пока proposed.

## Три разные сущности

**Inode** задаёт идентичность файла. **Version** задаёт неизменяемое содержимое inode в момент фиксации. **Chunk** — диапазон байт версии, отправленный отдельным document. Directory entry связывает parent_inode + name с inode.

Одинаковые SHA-256 и size у двух файлов не означают один inode. Hardlink в будущем — два имени одного inode. Symlink — собственный inode с target, без автоматического следования при восстановлении.

Для MVP имена — UTF-8, без NUL и `/`, с ограничением длины; `.` и `..` обрабатываются ядром TGFS. Полная поддержка произвольных Linux byte names вне UTF-8 пока не заявляется. Каталоги не обязаны иметь фиктивный document, пустой файл также не требует пустой загрузки.

## Удалённые записи

| Запись | Содержимое |
| --- | --- |
| Superblock | Короткое закреплённое text-сообщение: magic, format_version, fs_uuid, generation, commit_ref |
| Catalog document | Полный снимок directory entries, inode, опубликованных версий и ссылок на chunks |
| Commit | Короткая неизменяемая запись: fs_uuid, generation, operation_id, previous_commit_ref, catalog_ref, catalog_size, catalog_sha256 |
| Chunk document | Неизменяемые байты части; короткий диагностический caption |

Предлагаемая первичная упрощённая реализация каталога — полный снимок на commit, без журнала изменений. Цена — O(размер каталога) на публикацию; это ограниченный MVP для небольших томов. Каталог не должен превышать 16 MiB в cloud-профиле: при превышении публикация отклоняется **до** смены superblock. Для масштаба потребуется ADR о журнале/checkpoint или дереве метаданных; произвольный рост не обещается.

Catalog хранится как document с JSON в UTF-8. Хешируется точная последовательность загруженных байт, не результат повторной сериализации. Нельзя смешивать каталог незавершённой версии с подтверждёнными данными.

## Ссылка на объект

Транспортная ссылка включает backend, channel_id, message_id; для Bot API дополнительно сохраняются bot_id и file_id как ускорение скачивания. `file_unique_id` допустим для диагностики, но не для download. Ссылка не содержит bot token.

Идентификаторы разных backend — разные пространства: message_id TDLib нельзя считать равным message_id Bot API; raw-преобразования в core запрещены. Хранить типизированную ссылку и преобразовывать только проверенным адаптером. Большие идентификаторы передавать безопасно для 64-bit, например десятичными строками в JSON.

`file_id` может быть недействителен для другого бота. Поэтому адрес исходного сообщения сохраняется вместе с ним. Перенос на другой бот требует восстановить доступ к документам, а не только скопировать SQLite.

## Superblock и caption — эскиз

```json
{"magic":"TGFS","format_version":1,"fs_uuid":"<uuid>","generation":7,"commit_ref":{"backend":"bot_api","channel_id":"-1001234567890","message_id":"1042"}}
```

Пример полей caption, не готовый валидный объект:

```text
TGFS/1 chunk fs=<uuid> inode=<uuid> version=<uuid> part=0/3 offset=0 size=16777216 sha256=<64 hex>
```

Размер и SHA-256 целого файла, полный список chunk refs и Unix-метаданные находятся в каталоге версии. Уточнение пользователя: общий хеш и исходный размер нужны также в caption для распознавания повторных загрузок; обновлённый формат подписи ещё не утверждён. Для каждой части нужны part_index, offset, part_size, part_sha256 и object_ref. Все диапазоны непрерывны, не пересекаются, сумма размеров равна размеру файла. `part_index` начинается с 0. Caption не содержит весь путь или каталог; укладывается в предел Bot API 1024 символа и отправляется без parse_mode.

Обнаружение конца определяется количеством частей и их диапазонами. Расширения `file.ext.1` нужны только человеку. Полный hash+size — проверка содержимого; коллизии не используются для объединения inode. Предварительное предотвращение повторных загрузок не обязательно; чтение должно терпеть их, а механизм очистки требуется отдельно (см. ниже).

## Инициализация

1. Явная команда init проверяет доступ и права, существующий TGFS magic, channel_id и служебный канал при его использовании. mount и init различаются.
2. Создать уникальный fs_uuid и текстовый ACK; сохранить полученный ID локально как незавершённую инициализацию.
3. Загрузить каталог с root directory, затем commit generation=0.
4. Заменить ACK на superblock, указывающий на commit; закрепить и перепроверить чтение.
5. Сохранить superblock_message_id в профиле как резервный locator. Статус ready только после проверки.

Прерывание init не должно приводить к автоматической повторной «форматировке». Отдельная диагностика показывает созданные записи и варианты продолжения. Обычные и старые посты канала не удаляются; принадлежность определяется fs_uuid/magic и достижимостью из root, не диапазоном ID.

## Публикация версии

1. Подготовить байты и хеши в staging; выделить version_id и operation_id; записать intent в локальный durable-журнал.
2. Загрузить недостающие chunks. Сохранить ответы upload; неопределённые ответы могут породить недостижимые дубликаты, но не видимый полфайл.
3. Подготовить новый полный каталог только с завершёнными версиями, загрузить и сохранить его точный hash/size.
4. Отправить неизменяемый commit с предыдущим commit_ref.
5. Проверить ожидаемое поколение и обновить **существующее** сообщение superblock на новый commit_ref.
6. Сверить новое содержимое superblock и только затем подтверждать удалённую фиксацию. Установка pin нужна для bootstrap; не создавать новый pin на каждый chunk.

Шаг 5 — предлагаемая точка видимости. Предположение, что редактирование одной записи даёт читателю целый старый или новый JSON, нужно подтвердить экспериментом; это не транзакция Telegram и не compare-and-swap. Конкурентные writer запрещены контрактом, а не решены этим алгоритмом.

| Момент сбоя | Ожидаемое состояние |
| --- | --- |
| До обновления superblock | Старый каталог остаётся видимым; новые недостижимые объекты — кандидаты ручной диагностики |
| Во время update с потерянным ответом | Результат неизвестен; повторно читать и сверять generation, commit_ref и operation_id |
| После update, до локального ack | На remount виден целый новый каталог; intent сверяется с удалённым состоянием |
| Невозможно прочитать root после timeout | Остановить публикации и сообщить recovery required; не перезаписывать вслепую старым root |

Идемпотентность гарантируется логикой версии и operation_id, а не обещанием Bot API исключить дубли sendDocument.

## Mount без локального индекса

1. Получить superblock через getChat/pinned_message; убедиться в magic и ожидаемом fs_uuid.
2. Если возвращён другой pin или pin отсутствует, использовать явно сохранённый superblock_message_id. В Bot API прочитать известное сообщение можно попробовать через forwardMessage в служебный канал.
3. По точной ссылке получить commit, затем catalog document; проверить размер, SHA-256, версию и согласованность fs_uuid/generation.
4. Построить SQLite индекс. Проверять дубликаты имён, отсутствующих родителей, циклы каталогов, допустимость типов, диапазоны частей и лимиты parser до mount.
5. Скачать данные лениво при read, используя сохранённые file_id; при необходимости восстановить file_id по ссылке исходного сообщения.

Этот алгоритм не требует сканировать всю историю. Если утрачены и pin, и резервный locator, Bot API-only восстановление автоматически не гарантируется: потребуется известный ID, экспорт recovery-настроек либо пользовательский backend для поиска. При protected content пересылка недоступна; совместимость Bot API-профиля должна проверяться заранее.

Служебный канал должен быть отдельным, с минимальным доступом; source и staging не совпадают. Cleanup работает только с известными ID созданных TGFS копий, после обработки результата; не очищает чужие сообщения или источник. Нужны очередь повторов и явный статус, если удалить копию не удалось.

## Повторные загрузки и очистка дубликатов

Требование пользователя зафиксировано 2026-11-03. Две машины могут загрузить одинаковое содержимое независимо и оставить несколько комплектов сообщений. Это допустимая ситуация для чтения, но нежелательное состояние хранения. Нужен механизм обнаружения и очистки дубликатов: [задача #9](https://github.com/Hanan4ik/tgfs/issues/9). Предотвращение повторного upload заранее не является обязательным условием этого поведения.

Пример: файл hello.txt размером 30 МБ представлен двумя частями. Машина1 загрузила hello.txt.1 и hello.txt.2, затем Машина2 — ещё hello.txt.1 и hello.txt.2. Четыре сообщения не означают четыре последовательные части одного файла: это два кандидата на получение того же содержимого. Хеш в caption относится ко всему исходному файлу на 30 МБ, а не только к отдельной части.

Чтение: получить полный подходящий комплект, собрать части в правильном порядке, проверить исходный размер и общий SHA-256. После первой успешной сборки поиск альтернативных копий именно этого содержимого можно прекратить; оставшиеся дубликаты не добавляются к файлу и не обязаны скачиваться. Под «первым» понимается первый успешно проверенный комплект в выбранном порядке обхода, а не гарантия самого раннего сообщения канала. Проверка отдельных частей дополнительно полезна для random read.

В примере названия условные; имя и суффикс сами по себе не доказывают комплектность. Разбиение может различаться, а сообщения перемешиваться. Подбор по общему hash+size, количеству и диапазонам частей либо идентификатору upload требует отдельного решения; смешивание частей из разных загрузок допустимо только при доказанной совместимости диапазонов и итоговой проверке. Бесконтрольный перебор комбинаций не предлагается.

Это требование устойчивости к физическим дубликатам, а не дедупликация независимых имён, не hardlink и не выбор актуальной версии по одному имени. Оно также не разрешает одновременную публикацию каталога несколькими writer. Ранее предложенный каталог адресует части точными refs: обычное чтение остаётся по ним. Поиск другого комплекта — отдельная процедура импорта/восстановления. Полноценного сканирования истории Bot API в проекте нет; источник списка кандидатов (удалённый реестр известных upload/message_id либо иной способ) ещё предстоит спроектировать.

Для caption добавляется требование обозначить file_sha256 и file_size исходного файла отдельно от part_sha256 и part_size. Точные имена, кодирование и длина обновлённого caption ещё согласуются; прежние примеры не являются окончательной схемой.

Очистка проектируется отдельно от чтения:
- Сначала dry-run со списком конкретных известных message_id и основаниями избыточности.
- Сохраняемый полный комплект проверяется до удаления других; единственная проверенная копия не удаляется.
- Учитываются актуальный каталог, сохраняемые поколения истории, открытые файлы и незавершённые операции. При необходимости сначала публикуются ссылки на сохраняемый комплект; нельзя оставлять старые поддерживаемые каталоги со сломанными refs.
- Удаление сериализуется с загрузкой/публикацией либо проводится при остановленных writer; read-success само по себе не доказывает безопасность удаления.
- Неполная повторная загрузка отмечается отдельно; совпадение имени при другом содержимом не является дубликатом.
- Требуются журнал, повторяемость, обработка ошибок и сохранение неизвестных/непроверенных сообщений без удаления.
- Bot API deleteMessage ограничивает удаление возрастом менее 48 часов и правами; deleteMessages наследует ограничения. Недоступные для удаления объекты показываются как неочищенные. Полная очистка старого канала с выбранным backend не гарантируется.

Источник ограничения, проверен 2026-11-03: https://core.telegram.org/bots/api#deletemessage. Живые эксперименты не проводились. Принято требование терпимости к повторным загрузкам и необходимости очистки; конкретный алгоритм и этап реализации остаются открытыми.

## Удаление и история

unlink в TGFS меняет каталог. Он не гарантирует физического удаления документа из Telegram. Автоматическая очистка старых поколений пока не реализуется; требование очистки физических дубликатов выделено в #9, его этап и алгоритм ещё не выбраны. Bot API ограничивает удаление сообщений по возрасту; поэтому обычный GC старых данных через этот backend нельзя обещать. Retention, ручное обслуживание и GC с пользовательской авторизацией — отдельные будущие решения.
