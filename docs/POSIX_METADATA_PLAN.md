# План типов объектов, ссылок и Unix-атрибутов после MVP

Дата: 2026-11-03. Требование пользователя принято: после MVP обычных файлов и каталогов предусмотреть symbolic links, hard links и специальные биты прав. Точные wire-format, операции FUSE и числовое отображение владельцев остаются **proposed**. Это план расширения архитектуры, не реализация функций и не заявление полной POSIX-совместимости.

## Каталоги в Telegram

Каталог хранится служебными метаданными журнала в обычном текстовом сообщении, а не document с фиктивными байтами. Парсер читает Message.text. Включение отдельных каталоговых записей в первый прототип и точные названия типов/полей ещё согласуются в #2.

Пустой каталог тоже имеет метаданные и постоянный UUIDv4 object_id. Дочерние записи ссылаются на него через parent_object_id; пустота не означает отсутствие каталога. Корень уже объявляется SUPERBLOCK через root_object_id.

## Три слоя, которые нужно сохранять раздельными

| Слой | Содержимое | Почему важно |
| --- | --- | --- |
| Объект | object_id, тип и Unix-атрибуты | Файл не теряет идентичность при rename или chmod |
| Имя в каталоге | parent_object_id + name -> object_id | Несколько имён могут указывать на один объект для будущего hardlink |
| Содержимое | version_id, размер, общий хеш и refs CHUNK | Изменение прав или имени не требует загрузки новых байтов |

Не делать путь единственной идентичностью объекта и не хранить единственный parent/name как неотделимые свойства объекта. Это ограничило бы будущий hardlink. Обновления атрибутов не должны случайно возвращать старую версию bytes, а FILE_COMMIT содержимого — отменять более новые chmod/rename. Нужны отдельные правила порядка/версий метаданных; их wire-format ещё не выбран.

## Типы объектов

В модели предусматривается явный object_type, отличающий семантику объекта от типа записи журнала (type=FILE_COMMIT и т.п.). Имя поля object_type и точное кодирование — предложение.

| Тип объекта | Хранение | Этап |
| --- | --- | --- |
| regular | Версия bytes, refs частей и FILE_COMMIT | MVP |
| directory | Текстовые метаданные и связи имён; без data CHUNK | MVP |
| symlink | Собственный object_id и сохранённый target_path | После MVP |
| hardlink | Не отдельный тип объекта: дополнительное имя существующего object_id | После MVP |

Неизвестный тип или обязательную неподдержанную семантику нельзя выдавать как regular. Политику отказа/ограниченного read-only при mount нужно согласовать вместе с версией формата и feature flags.

## Символическая ссылка

Ссылка — самостоятельный объект со своим UUID; её содержимое — target pathname, а не UUID целевого файла. Пример смысла: /shortcut -> documents/video.mp4. Относительная цель интерпретируется относительно содержащего ссылку каталога. Цель может быть абсолютной, относительной или пока не существующей; она не подменяется автоматически найденным объектом.

Не раскрывать и не копировать цель при сохранении/восстановлении ссылки. Нужны readlink/symlink и lstat/getattr правильного типа, длина/кодирование target, ограничения разрешения циклов и правила доступа. В первом MVP эти функции не считаются работающими. Точный способ хранения target в текстовой записи либо document для больших метаданных ещё открыт.

## Жёсткая ссылка

Два имени одного файла указывают на один object_id, например:
- (D1, video.mp4) -> F1;
- (D2, backup-name.mp4) -> F1.

Изменение содержимого через любое имя меняет один и тот же объект. Это не физический дубль CHUNK и не автоматическое объединение двух файлов по одинаковому SHA-256. Оба имени в пределах одного mount относятся к одному локальному inode, хотя на другой машине числовое значение inode может быть иным.

Нужны операции link/unlink, st_nlink и учёт достижимости. Отдельное удаление имени не удаляет объект, пока остаются другие имена; открытые handles/сохраняемые версии также учитываются cleanup. Авторитетный счётчик ссылок, конкурентные link/unlink и политика ссылок на каталоги ещё согласуются. Нельзя обещать безопасность удаления по одному локальному счётчику.

## Права, владельцы и специальные биты

Имеются в виду специальные **биты**, а не байты содержимого файла.

| Атрибут | Назначение | Открытый вопрос |
| --- | --- | --- |
| mode: rwx | Права owner/group/other | Проверки доступа, umask и chmod |
| sticky, 01000 | Для каталога ограничивает удаление/переименование чужих entries | Кто считается владельцем на разных машинах и где исполняется проверка |
| setgid, 02000 | Специальная семантика группы; в каталоге влияет на группу создаваемых объектов | Наследование, chown/chmod и локальная политика mount |
| setuid, 04000 | Специальная семантика effective UID исполняемого файла | Разрешено ли применение; сохранение атрибута отдельно от его исполнения |
| uid/gid | Владелец и группа объекта | Совпадают ли пространства пользователей разных машин; remapping |
| atime/mtime/ctime | Времена доступа, изменения содержимого и метаданных | Единицы, источники времени, частота удалённых обновлений |
| btime | Время создания, если поддерживается | Нужность и переносимость; ctime не является временем создания |

Предложение представления mode: отдельный тип объекта и строка четырёх восьмеричных цифр с разрешённой маской 07777 (например "0644" или "1777"). В JSON нет восьмеричных числовых литералов; строка избегает путаницы с десятичным числом 1777. Конкретная схема ещё не утверждена. При формировании st_mode тип добавляется адаптером.

Сохранять биты в метаданных и реально применять их — разные задачи. Sticky на обычном файле не означает запрет его редактирования; на Linux значимая описанная здесь семантика относится к каталогу. Setuid/setgid нельзя считать поддержанными только потому, что поля возвращены в getattr.

Числовые uid/gid одного пользователя на разных машинах могут отличаться, а одинаковый номер может относиться к разным людям. Нужна явная политика: сохранённые номера, локальное отображение либо mount owner. Имена Telegram sender не заменяют Unix-владельцев. До согласования политики не обещать переносимость проверок прав.

## Дальнейшие расширения

xattr, ACL и flags вроде immutable/append-only — отдельные механизмы, не ещё несколько rwx/sticky-битов. Предусмотреть версионируемые изменения метаданных и явное описание поддержанных возможностей. Не добавлять фиктивную поддержку mmap, locks, sparse, device nodes/FIFO/socket через успешные ответы без соответствующих гарантий. Они остаются отдельными вопросами #3.

Сначала реализуется согласованный MVP regular/directory. Затем принимаются конкретные схемы и FUSE-контракты расширений. Unsupported operations должны явно сообщаться приложению; конкретные errno и mount-policy ещё требуют решения.

## Критерии будущей проверки

- Пустая папка восстанавливается после удаления локального индекса.
- Relative, absolute и dangling symlink сохраняют точный target; чтение метаданных не раскрывает цель.
- Два hardlink имеют один object_id/локальный inode на mount; изменение через одно имя видно через другое; удаление одного имени сохраняет второе.
- Последний unlink и открытый handle не приводят к преждевременному удалению remote bytes.
- Chmod не создаёт новую версию содержимого и не отменяется поздним FILE_COMMIT старого snapshot.
- Sticky-каталог проверяется владельцем файла, владельцем каталога и другим пользователем; режим не трактуется как payload.
- UID/GID remapping и setuid/setgid ведут себя по выбранной политике, а не по случайному совпадению номеров.
- Старый клиент явно реагирует на новые обязательные типы/атрибуты.

Проверки не выполнены. См. [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#9](https://github.com/Hanan4ik/tgfs/issues/9), [F49 и другие открытые сценарии](UNRESOLVED_FAILURE_SCENARIOS.md).
