# Ограниченный ремонт backlinks

Реализован явный режим `tgfs intent --repair-backlinks`. Обычный intent
остаётся диагностическим и не выполняет изменяющих API запросов.
Это ремонт captions существующих CHUNK, не полное resume загрузки.

## Условия

- Поддержан только put: подтверждённый канонический FILE_COMMIT и verified
  staging/CHUNK/refs. При ненаблюдённых, неоднозначных частях или конфликтующем
  ненулевом backlink режим завершается ошибкой до редактирования.
- Новые CHUNK/FILE_COMMIT/ADD не отправляются. Допускается ремонт частей create,
  чей commit найден, но ADD ещё отсутствует; имя при этом не публикуется.
- Изменяются только file_commit_id и next_message выбранных частей. Данные,
  UUID, хеши и прочие поля сохраняются. FILE_COMMIT/DIRECTORY не редактируются.

## Повторная проверка перед записью

При наличии предложенных исправлений повторно проверяется закреп SUPERBLOCK.
Затем канонический FILE_COMMIT и все затронутые CHUNK пересылаются в служебный
канал, указанный в capture. Проверяются forward_origin, исходный/служебный
каналы, ID, document filename/size и содержимое (file_id может иметь несколько валидных значений) и неизменяемые поля captions.
Используется свежий caption, а не слепая перезапись caption из старого capture.
При расхождении редактирование блокируется. Все запланированные сообщения
проверяются перед первым storage edit. Служебные копии удаляются после чтения.

Уже исправленная часть пропускается без editMessageCaption. Остальные получают
ожидаемые file_commit_id/next_message; ответ редактирования сверяется по ID,
каналу, документу и полному caption. Автоматических сетевых retries нет.
Запросы изменений в production разделяются задержкой 1100 ms; это не отменяет
возможность 429. Тестовый бинарник пропускает задержки.

Bot API не предоставляет compare-and-swap caption: проверка и edit не являются
атомарной транзакцией. Это не распределённая блокировка между машинами.
Режим предполагает неизменность смысловых полей опубликованных TGFS сообщений;
параллельный корректный ремонт тех же ссылок задаёт те же значения.

## Журнал и повторный запуск

В state-dir открывается backlink-repair.log (0600, обычный файл текущего
пользователя, без symlink/hardlink), берётся неблокирующая эксклюзивная flock.
Второй ремонт этого state-dir отвергается. Журнал дописывается с fsync:
service_channel, forward_pending, service_copy_known/service_copy_deleted,
edit_pending/edit_confirmed. Значения содержат channel/message ID, не токен.

При потере ответа edit могла выполниться. Повторный явный запуск снова читает
текущее сообщение и пропускает уже исправленное. Не нужно вручную удалять лог
или intent. Фаза intent.json не меняется: ремонт backlinks не означает
завершения всех этапов первоначального put. data.bin также сохраняется.

Если ответ forward потерян, ID служебной копии может остаться неизвестен.
Если ID известен, он сохраняется до cleanup. При ошибке очистки режим
останавливается; оставшиеся копии требуют диагностики по логу и capture.
Лог не включается автоматически в cleanup_pending сканера. Слепое повторение
не гарантирует отсутствия оставшейся служебной копии; оригиналы не удаляются.

## Результат

Сохраняются поля диагностического отчёта и добавляются:

- repair_applied=true — режим успешно завершил проверки/применение;
- repaired_chunk_ids — части, редактирование которых подтверждено;
- repair_skipped_ids — части из старого плана, уже имеющие нужные ссылки.

repair_applied=true с пустым repaired_chunk_ids — допустимый no-op.
Если исходный план не пуст, next_step=capture_after_repair: нужен новый scan
для подтверждения обновлённых captions. backlink_repairs остаётся планом
входного capture, а не пересчитанным остатком. can_resume/resumed остаются
false: отправка новых данных и полное resume не выполняются.
При ошибке успешный JSON не печатается, код1 и причина идут в stderr;
часть изменений могла состояться, известные этапы остаются в логе.

## Живой тест без искусственного повреждения

Пользователь подтвердил put intent: commit41/CHUNK40, verified staging и пустой
backlink_repairs. На этом состоянии команда должна выполнить no-op:

```bash
git pull --ff-only
make
./build/tgfs intent "${tgfs_net[@]}" \
  --state-dir "$HOME/.local/state/tgfs/replace-documents-hello-001" \
  --capture ./capture-010 \
  --repair-backlinks
```

Ожидаются repair_applied=true, repaired_chunk_ids=[], repair_skipped_ids=[].
При пустом плане служебные пересылки и storage edits не выполняются; новый
scan не нужен. Не нужно вручную ломать captions для проверки реального ремонта.
Непустой ремонт после сбоев проверен HTTP double; живое выполнение при реальном
незавершённом intent ещё предстоит проверить.

114 тестовых методов; расширенные сценарии покрывают lost edit response,
идемпотентный повтор со старым capture, ошибку origin/cleanup/pin, изменённый
caption, ambiguous parts, no-op и flock. Проверяются неизменность intent и
отсутствие новых data/commit/directory публикаций. Локально 110 passed и 4
kernel skips из-за отсутствия /dev/fuse; ASan/UBSan с detect_leaks=0 из-за ptrace.
