# Создание hello.txt: низкоуровневый контракт v0.1

Дата: 2026-11-03. Статус: proposed. Это конкретизация PROTOCOL.md, не принятый стабильный формат и не работающая реализация. Bot API выбран, FUSE и write-контракт ещё обсуждаются. Задачи #2, #3, #5; эксперименты #6 и #7 не проводились.

## 1. Условия и ожидаемый результат

Уже инициализирован том, один writer на одном хосте. Основной канал -1001234567890; superblock — сообщение 100; поколение 0 содержит только корневую папку. Нет стороннего редактирования служебных сообщений. Служебный канал используется только по известным ID при восстановлении, не для перебора диапазона.

Создаём /hello.txt с текстом Привет без BOM и перевода строки. UTF-8: 12 байт, hex d09fd180d0b8d0b2d0b5d182, SHA-256 dd679c0b9fd408a04148aa7d30c9df393f67b7227f65693fffe0ed6d0f0ade59. Размер считается в байтах, не символах.

Сценарий условно выражен create -> write -> fsync(file) -> fsync(parent) -> close. Это описание обращений, а не готовая shell-команда: printf и обычное закрытие файла сами по себе не гарантируют fsync. Редактор может использовать temp + rename, рассмотрено ниже.

## 2. Идентификаторы и адреса

- fs_uuid — постоянная идентичность тома, inode_id — объекта файла, version_id — его содержимого, operation_id — попытки фиксации. В примерах UUID используются настоящего формата, но значения демонстрационные.
- generation — целое число опубликованного состояния. Не равно Telegram message_id.
- inode_id постоянен при rename; version_id меняется при изменении содержимого.
- Идентификаторы Telegram и потенциально большие размеры/смещения передаются в JSON десятичными строками без знака + и ведущих нулей (кроме 0); channel_id знаковый. После разбора проверяем диапазон signed 64-bit и неотрицательность size/offset.
- Малые поля generation, part_index/part_count — JSON integers в пределах 0..2^53-1 с проверкой переполнения.
- Ссылка на сообщение: backend + channel_id + message_id. Ссылка на document дополнительно имеет bot_id и file_id; последние — кэш доступа для конкретного бота.
- message_id узнаём из ответа API. ID ниже условные, не обязаны идти подряд. Никогда не предсказываем следующий ID.

## 3. Superblock: закреплённый указатель

Это text-сообщение 100; при публикации меняется его текст, а ID остаётся тем же.

```json
{
  "magic": "TGFS",
  "format_version": 1,
  "fs_uuid": "11111111-1111-4111-8111-111111111111",
  "generation": 1,
  "commit_ref": {
    "backend": "bot_api",
    "channel_id": "-1001234567890",
    "message_id": "113"
  }
}
```

magic отличает TGFS от обычного поста. format_version определяет правила разбора; незнакомая версия приводит к отказу записи. fs_uuid сверяется с профилем и зависимыми записями. generation и commit_ref выбирают подтверждённый root.

Здесь не нужны start_id/last_used_id, имена всех файлов, токен или параметры прокси. Собственный ID superblock хранится в профиле как locator и берётся из Message. Размер текста ограничиваем 4096 символами, сериализуем без Markdown parse_mode. Пин не заменяет резервный locator.

## 4. Chunk: байты, отправляемые document

Файл меньше предлагаемого C=16 MiB: отправляем один document; его содержимое — ровно 12 байт. Telegram filename может быть техническим, например tgfs-<version_id>-0.bin: пользовательское имя берётся из каталога.

Эскиз caption (одна строка, без parse_mode):

```text
TGFS/1 chunk fs=11111111-1111-4111-8111-111111111111 inode=33333333-3333-4333-8333-333333333333 version=44444444-4444-4444-8444-444444444444 part=0/1 offset=0 size=12 sha256=dd679c0b9fd408a04148aa7d30c9df393f67b7227f65693fffe0ed6d0f0ade59
```

Caption — диагностическая маркировка; источник истины для опубликованного тома — каталог. Проверяем длину <=1024 символов. Ответ sendDocument даёт message_id=110 и document.file_id. Сначала сохраняем этот ответ в локальный журнал, потом строим каталог. Поле bot_id — ID из getMe, не токен.

## 5. Catalog document: всё дерево в одном снимке

Загружаем UTF-8 JSON отдельным document, в примере message_id=112. Минимальная структура после создания:

```json
{
  "magic": "TGFS_CATALOG",
  "format_version": 1,
  "fs_uuid": "11111111-1111-4111-8111-111111111111",
  "generation": 1,
  "root_inode_id": "22222222-2222-4222-8222-222222222222",
  "inodes": [
    {
      "inode_id": "22222222-2222-4222-8222-222222222222",
      "type": "directory"
    },
    {
      "inode_id": "33333333-3333-4333-8333-333333333333",
      "type": "regular",
      "version_id": "44444444-4444-4444-8444-444444444444",
      "size": "12",
      "sha256": "dd679c0b9fd408a04148aa7d30c9df393f67b7227f65693fffe0ed6d0f0ade59",
      "part_count": 1,
      "parts": [
        {
          "part_index": 0,
          "offset": "0",
          "part_size": "12",
          "part_sha256": "dd679c0b9fd408a04148aa7d30c9df393f67b7227f65693fffe0ed6d0f0ade59",
          "object_ref": {
            "backend": "bot_api",
            "channel_id": "-1001234567890",
            "message_id": "110",
            "bot_id": "123456789",
            "file_id": "EXAMPLE_FILE_ID_NOT_USABLE"
          }
        }
      ]
    }
  ],
  "entries": [
    {
      "parent_inode_id": "22222222-2222-4222-8222-222222222222",
      "name": "hello.txt",
      "inode_id": "33333333-3333-4333-8333-333333333333"
    }
  ]
}
```

file_id демонстрационный. SHA-256 содержимого посчитан, но этот JSON не является загруженным документом. Хеш каталога вычисляется по точным сериализованным байтам, включая пробелы/переводы строк, а не по «эквивалентному JSON».

Имя отделено от inode: rename меняет entries, а содержимое может остаться прежним. Имена уникальны внутри parent, UTF-8, 1..255 байт, без / и NUL, не . и не ... Последнее означает запрет имени из двух точек: "..". В JSON нет абсолютных путей, которые нужно создавать на локальном диске при восстановлении.

Минимальный MVP отображает UID/GID/mode по политике mount, стабильные времена и chmod/chown пока не обещаются. Если требуется сохранять времена — отдельно утвердить поля mtime_ns/ctime_ns и их правила; не выдумывать Unix-владельца из Telegram sender.

## 6. Commit: запись завершённого состояния

Отдельное неизменяемое text-сообщение 113 связывает каталог с предыдущим поколением:

```json
{
  "magic": "TGFS_COMMIT",
  "format_version": 1,
  "fs_uuid": "11111111-1111-4111-8111-111111111111",
  "generation": 1,
  "operation_id": "55555555-5555-4555-8555-555555555555",
  "previous_commit_ref": {
    "backend": "bot_api",
    "channel_id": "-1001234567890",
    "message_id": "103"
  },
  "catalog_ref": {
    "backend": "bot_api",
    "channel_id": "-1001234567890",
    "message_id": "112",
    "bot_id": "123456789",
    "file_id": "EXAMPLE_CATALOG_FILE_ID_NOT_USABLE"
  },
  "catalog_size": "<exact serialized byte length>",
  "catalog_sha256": "<computed SHA-256 of exact catalog bytes>"
}
```

Последние два значения — явно обозначенные места для вычислений, не валидные значения wire-format. Для generation=0 previous_commit_ref=null.

Зачем отдельный commit? Он сохраняет неизменяемую связь состояния и предшественника, пока superblock перезаписывается. Это дополнительный API-запрос; упрощение со ссылкой прямо на каталог возможно отдельным решением. Наличие commit-сообщения ещё не публикует файл: публикацией считается смена указателя superblock.

## 7. Состояния одной операции

| Состояние | Работа | Можно ли подтвердить удалённый fsync? |
| --- | --- | --- |
| DIRTY_LOCAL | create/write меняют локальный вид; сохранить intent и staging | Нет |
| PREPARED | Заморозить snapshot байтов, посчитать размеры/хеши, сделать локальные файлы и intent durable | Нет |
| DATA_UPLOADED | Загружены части, ответы записаны локально | Нет |
| CATALOG_UPLOADED | Загружен полный новый каталог | Нет |
| COMMIT_SENT | Отправлен commit, старый superblock пока активен | Нет |
| ROOT_UPDATE_UNKNOWN | Запрос обновления отправлен, результат неизвестен | Нет |
| PUBLISHED | Повторное чтение superblock подтвердило ожидаемый generation и commit_ref | Да, для зафиксированной версии |
| RECOVERY_REQUIRED | Результат публикации проверить нельзя | Нет; новые публикации приостановлены |

При freeze новые записи в тот же inode можно блокировать до завершения операции для первого простого варианта; нельзя хешировать одновременно изменяемый staging. Любая публикация сериализована общей очередью тома. В новый каталог попадают только полные версии; другие dirty inode остаются локальными.

При fsync файла предлагается вместе с ним публиковать запись нового имени и родительскую связь (усиленная гарантия для этого сценария). fsync(parent) остаётся явным барьером каталога и не требует нового поколения, если изменений больше нет. Для rename/delete контракт уточняется ниже. Только fsync(file) без существования parent не должен создавать «потерянный inode».

Локальные этапы требуют записи данных, fsync staging/журнала и нужных каталогов локального диска; транзакция SQLite не делает произвольный staging-файл durable автоматически. После crash незавершённый staging не становится опубликованной версией.

## 8. В итоге в канале

| ID (пример) | Вид | После фиксации |
| --- | --- | --- |
| 100 | Superblock | Текст изменён: generation=1, commit_ref=113 |
| 102 | Catalog generation 0 | Сохранён как история |
| 103 | Commit generation 0 | Сохранён |
| 110 | Chunk hello.txt | 12 байт |
| 112 | Catalog generation 1 | Содержит новое имя и ref=110 |
| 113 | Commit generation 1 | Ссылается на catalog=112, previous=103 |

Добавлены три сообщения и одно редактирование, без учёта проверочных чтений/recovery и служебных событий Telegram. Не редактируем старые chunks и catalogs. Для K частей: K documents + catalog document + commit text + update superblock. Полный каталог на каждую фиксацию дорог при росте тома; предел 16 MiB пока ограничивает MVP.

## 9. Чтение на другом компьютере

Прочитать superblock, проверить magic/version/fs_uuid; получить точно commit=113 через известный ID и при необходимости forwardMessage в служебный канал; получить каталог через getFile с catalog file_id; проверить catalog_size/hash; построить индекс. Для hello.txt найти entries -> inode -> part.ref; скачать и проверить 12 байт/SHA-256. При другом боте file_id обновлять через известное исходное сообщение. Список всех ID канала не нужен.

Источник методов: https://core.telegram.org/bots/api (getChat, forwardMessage, getFile, sendDocument, editMessageText). forwardMessage создаёт копию и возвращает Message; protected content исключает такой путь. Полученные копии чистим только по известным ID. Superblock читаем через pin, а при неподходящем pin — через сохранённый ID с проверкой источника пересылки.

## 10. Сбои и retry

| Сбой | Действие |
| --- | --- |
| Upload части/каталога/commit оборвался | Старый root активен. Повтор может создать дубликат, но только выбранные refs публикуются |
| Update superblock дал timeout | Не отправлять вслепую новую операцию: прочитать исходный superblock |
| Там ожидаемый commit | Операция опубликована; восстановить локальный журнал |
| Там прежний commit | После проверки отсутствия другого writer допускается повторить точное обновление; это не CAS |
| Там другое поколение/commit | Конфликт: остановить запись, диагностика; не перезаписывать |
| Superblock недоступен | RECOVERY_REQUIRED; не выдавать успех |
| Root ссылается на повреждённый каталог | Отказать mount; старое поколение только через явное recovery, без тихого отката |
| Локальный диск переполнен | ENOSPC, dirty staging не удалять |
| Telegram rate limit | Ограниченная очередь и retry_after; timeout системного вызова не должен превращаться в бесконечное ожидание |

Один writer — эксплуатационное ограничение. Проверка поколения не защищает от гонки двух хостов. Хеши проверяют целостность, но не аутентичность против администратора канала, способного заменить и данные, и хеши. Отдельной подписи пока нет.

## 11. Из этого следуют остальные операции

| Случай | Изменения формата |
| --- | --- |
| Пустой файл | size=0, part_count=0, parts=[], SHA-256 пустых байтов; chunk не отправлять |
| Большой файл | N=ceil(size/C); упорядоченные части; при точном кратном C пустой хвост не отправлять |
| Создать папку | inode type=directory и entry, без data document |
| Rename | Новый каталог с изменённым entry; прежние chunks переиспользуются |
| Перезаписать | Тот же inode, новый version_id, новые/переиспользованные неизменяемые части |
| Удалить | Удалить entry, inode после последнего имени и открытого handle; физическая чистка Telegram отдельно |
| Открытый файл после unlink | Handle держит конкретную версию локально; старые remote chunks не чистятся |
| temp -> fsync -> rename -> fsync(parent) | Сначала может быть опубликован temp, затем новое поколение с конечным именем; rename не публикует частичный файл |

Для multipart проверяем part_index=0..N-1, непрерывность offset, положительный размер каждой части, sum(part_size)=size и хеш каждой части; хеш всего файла проверяем при полном чтении/verify. Контрольные размеры: 0, C-1, C, C+1, 2C, 2C+1.

## 12. Локальные низкоуровневые сущности

Предлагаемая SQLite-схема логически: volume(fs_uuid, confirmed_generation, commit_ref); inodes; entries с UNIQUE(parent,name); versions; parts; intents(operation_id, expected_generation, target_generation, state, staged_paths, uploaded_refs, target_commit_ref); cleanup_queue только для служебных копий. Dirty и confirmed состояния не смешивать. Нужны external staging-файлы, cache частей и таблица открытых handles в памяти.

Стабильный UUID inode отображается в числовой FUSE nodeid через локальную таблицу; Telegram message_id и хеш не выдаются как inode number. Root nodeid резервируется адаптером. Счётчики открытых дескрипторов и lookup/references FUSE ведутся отдельно; освобождение handle не удаляет подтверждённые данные. Точная схема БД и FUSE binding после выбора языка.

Парсер отклоняет дубликаты JSON-ключей, неподдерживаемые типы, дубликаты имён/inode, отсутствующих родителей, циклы, переполнения, неверные refs и несовпадение fs_uuid/generation. Не исполняет имена, captions или JSON. Ограничивает размер каталога до разбора, число сущностей и глубину; точные пределы кроме 16 MiB требуют отдельного согласования. JSON без компрессии в первом варианте.

## 13. Граница готовности

Сценарий конкретизирует формат и отказные состояния. До accepted нужно согласовать: отдельный commit или прямой указатель, стоимость полного каталога, усиленный fsync новой записи, close/flush без явного fsync, семантику времён/прав и локальный recovery. Язык, библиотека, cloud/local и лимиты очередей не выбраны. Нельзя считать все низкоуровневые вопросы закрытыми одним примером.
