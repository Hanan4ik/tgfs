# Решения для основного сценария MVP и отложенная обработка ошибок

Дата: 2026-11-03. Запись ответов пользователя на вопросы о создании файла, каталогах, списке частей и сбоях. Это документация проектирования, не реализация и не результаты испытаний. Связи: #2, #3, #5, [#10](https://github.com/Hanan4ik/tgfs/issues/10).

## 1. Создание файла и FILE_COMMIT

Принято ранее и подтверждено: после отправки FILE_COMMIT captions выбранных CHUNK дополняются file_commit_id. Читатель переходит к публикации и сверяет идентичность объекта/версии, ссылки и характеристики частей. Непустой файл получает имя из document.file_name по последней точке, parent_id в caption ссылается только на директорию.

Уже принятое правило сохраняется: точка публикации — FILE_COMMIT, а не завершение редактирования всех captions. Частично заполненные backlinks после сбоя не отменяют публикацию; null не доказывает отсутствие commit. Прямые refs из FILE_COMMIT/манифеста остаются способом сборки. Ссылка из части не заменяет проверку её включения в commit.

Открыто: точное правило появления имени в каталоге при первой публикации, порядок обновления document каталога относительно FILE_COMMIT и представление имени пустого файла без CHUNK. Наличие backlink само по себе эти вопросы не решает.

## 2. Каталог как document

Уточнение пользователя: выбран вариант записей name + object_id, без file_commit_id. Document каталога содержит массив entries с такими записями. Массивы Telegram ID частей в DIRECTORY заменены этим вариантом; точные refs частей остаются в FILE_COMMIT.

Caption каталога содержит object_id и parent_id, общие поля распознавания TGFS и next_message. При переотправке document его исходный message_id меняется, object_id каталога сохраняется. Имя и тип дочернего объекта разрешаются через entries и собственный восстановленный индекс экземпляра.

Схема: [DIRECTORY_V1.md](DIRECTORY_V1.md). Чтение: [READ_PROTOCOL.md](READ_PROTOCOL.md). Выбор актуального DIRECTORY, родитель корня и порядок публикации имени с первой версией пока не меняются и остаются открытыми. Центральный координатор не вводится.

История решения: первоначально предлагался object_id → [telegram_id частей]; затем ассистент предложил name + object_id + file_commit_id. Пользователь выбрал имя и object_id, исключив ID commit.

## 3. Список parts в document

Выбрано направление: перенести список parts FILE_COMMIT в document, чтобы его размер не ограничивался длиной текста Telegram. Прежние примеры текстового FILE_COMMIT с inline parts сохранены в [FILE_COMMIT_V1_TEXT_HISTORY.md](FILE_COMMIT_V1_TEXT_HISTORY.md); они больше не определяют окончательное размещение parts. Текущее описание структуры: [FILE_COMMIT_V1.md](FILE_COMMIT_V1.md), навигация по CHUNK/DIRECTORY/FILE_COMMIT — [README.md](README.md).

Рабочее предложение ассистента: отправлять FILE_COMMIT одним document с описанием версии и parts, а в caption оставлять тип, идентификаторы и служебные ссылки. Завершённая отправка такого сообщения после частей служила бы публикацией версии.

Это ещё не окончательный wire-format. Нужно выбрать между всем FILE_COMMIT в document и отдельным document-манифестом, на который ссылается FILE_COMMIT; определить распределение полей, проверку документа и предел его размера. Сам перенос в document не означает неограниченного размера списка.

Для пустого файла по-прежнему нет CHUNK и байтов-заглушек; parts пуст. Прежняя текстовая оболочка пустого FILE_COMMIT требует согласования с новым размещением. Вариант отдельного commit-document для пустого файла — предложение, не обязательный CHUNK нулевого размера.

## 4. Сбои: отложенная задача

Пользователь хочет сначала продвигаться по успешному сценарию MVP, не проектируя сейчас все ветви восстановления. Требование будущей классификации принято; подробные классы, retry, errno и recovery отложены в [#10](https://github.com/Hanan4ik/tgfs/issues/10).

Будущий охват: API unreachable, явный API error, API unanswered/неизвестный результат, временные ограничения, локальное хранение/процесс/ОС и ошибки файловых операций. Это начальные группы для проработки, не принятый enum программы. Эксперименты #6/#7 и каталог F01–F51 не считаются выполненными.

## 5. Несостыковки формата и данных

В #10 отдельно требуется классифицировать непрохождение проверок: JSON и обязательные поля, типы/кодирование/версии, ссылки и тип родителя, filename/индекс, комплектность и диапазоны, размеры и SHA-256. Для каждого класса позже выбрать последствия и действие.

Наглядный пример: metadata описывают 5 байт hello и их SHA-256, а document содержит 5 байт jello. Проверка размера проходит, проверка хеша — нет. Это отличается от ошибки JSON и требует своего класса.

Повторное скачивание с последующим EIO обсуждалось как возможное поведение, но не принято как универсальная политика. Точные решения сейчас не фиксируются; непроверенные или повреждённые байты не объявляются корректными из-за наличия commit.

## Следующий шаг

Разобрать успешный сценарий directory-document + FILE_COMMIT с parts в document: выбрать точное размещение полей и последовательность публикации имени, содержимого и каталога. После этого составить план модулей C и чтения на втором экземпляре с восстановлением локального индекса. Программирование ещё не начато.
