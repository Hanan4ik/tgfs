# Постоянный индекс и кэш чтения

Дата: 2026-11-15. `tgfs read` теперь по умолчанию использует SQLite >= 3.31.
Сохраняются индекс записей выбранного capture, metadata documents и проверенные
байты CHUNK. Capture остаётся обязательной точкой входа и границей чтения.

## Сборка

Arch/CachyOS: `sudo pacman -S --needed sqlite`.
Debian/Ubuntu: `sudo apt-get install libsqlite3-dev`.
Остальные зависимости прежние: C11, Make, OpenSSL и libcurl; тесты — Python 3.
После установки зависимости: `make`.

## Проверка на пользовательском capture-006

```bash
tgfs_read=(
  ./build/tgfs read
  --capture ./capture-006
  --token-file "$HOME/.config/tgfs/secrets/test.token"
  --proxy socks5h://127.0.0.1:10808
  --cache-stats
)

"${tgfs_read[@]}" ls /
"${tgfs_read[@]}" ls /
"${tgfs_read[@]}" cat /multipart.txt
"${tgfs_read[@]}" --offline cat /multipart.txt
"${tgfs_read[@]}" --offline cat /empty.txt
```

При холодном кэше первый ls скачивает DIRECTORY/FILE_COMMIT; второй показывает
`cache: index=hit ... downloads=0`. Первый cat скачивает три части multipart;
повторный offline cat выдаёт `abcdefghij` с переводом строки, без запросов
к Telegram. Пустой файл выдаёт EOF и код 0. Если кэш уже прогрет, downloads
могут быть нулевыми и при первом запуске этой последовательности.

В обычном режиме каждый запуск делает getChat для проверки канала. downloads
считает скачанные documents/CHUNK, не getChat. `--offline` не делает запросов
вообще, но требует локальный файл токена для определения прежнего bot ID.
Его секрет офлайн не проверяется сервером: это доступ к уже полученным
локальным данным. Если нужный документ/часть не закэширован или вытеснен,
offline завершается ошибкой. Самостоятельного переключения в offline при
сетевой ошибке нет.

## Размещение и параметры

| Параметр/путь | Назначение |
| --- | --- |
| $XDG_CACHE_HOME/tgfs/index.sqlite3 | SQLite, если XDG_CACHE_HOME абсолютный |
| ~/.cache/tgfs/index.sqlite3 | Fallback при абсолютном HOME |
| --cache-dir DIRECTORY | Другой приватный каталог кэша |
| --cache-limit-mib N | Сумма bytes в таблице blobs: 1..4096 MiB, по умолчанию 256 |
| --cache-stats | index hit/miss, число blob hits и downloads в stderr |
| --offline | Только локальные index/documents/CHUNK |
| --refresh-cache | Заново скачать metadata и выбранные cat части, перестроить этот индекс |
| --no-cache | Прежний режим временного metadata workspace, без открытия SQLite |

Каталог создаётся с 0700, база с 0600. Существующие общедоступные каталоги,
неподходящие владельцы, symlink конечного каталога/файла и специальные файлы
отвергаются. Каталог назначения можно создать заранее с 0700. Неподдерживаемая
схема, посторонняя SQLite-база и повреждённая база автоматически не стираются:
для диагностики доступны --no-cache либо другой --cache-dir.

Параметры --no-cache несовместимы с cache-dir/limit/offline/refresh;
--offline несовместим с --refresh-cache. stdout остаётся данными ls/cat.
При поздней ошибке cat в stdout может остаться проверенный префикс: всегда
проверяйте код возврата.

**Кэш восстанавливаемый.** Он отделён от ~/.local/state/tgfs/... с intents
и staging загрузок. Эти intents могут содержать единственные неподтверждённые
байты; их нельзя удалять вместе с кэшем. Новые capture-каталоги read не создаёт:
следующий пользовательский scan по-прежнему capture-007.

## Схема и идентичность

| Таблица | Содержимое |
| --- | --- |
| captures | SHA-ключ capture, проверенный snapshot adapter, его SHA-256 и порядок использования |
| records | Исходный message_id, object_id/type и исходная JSON запись, привязанные к capture |
| records_by_object | SQL-индекс capture/object_id/source_id |
| blobs | Documents/CHUNK, SHA-256 содержимого и порядок использования |

SQLite application_id=TGFS, user_version=1. Схема, индекс и строки records
публикуются транзакциями. Проверка/создание схемы сериализованы с другими
открывающими процессами; busy timeout — 5 секунд. sqlite3_exec/prepare получают
фиксированный SQL, входные значения передаются через bind. Индекс capture
сохраняется только после успешной загрузки metadata существующим ядром.
Это не утверждение целостности всех байтов файлов: CHUNK проверяются при cat.

Namespace документа учитывает версию локального формата, публичный bot ID,
storage_chat_id, root_object_id и start_id. Ключ документа дополнительно
содержит source ID, type, file_id, file_size, а для CHUNK — part_sha256.
Секрет токена/прокси не записывается. file_id остаётся bot-specific metadata.
Ключ capture учитывает namespace и SHA-256 полного разобранного journal.json,
включая captions и границу. Изменение даже одного caption даёт новый индекс.
Порядок ключей JSON может вызвать лишний miss, но не выбор старого индекса.

После нового scan передайте новый --capture. Неизменившиеся документы из
старого capture переиспользуются по их идентичности; новые DIRECTORY ADD/REMOVE
и FILE_COMMIT применяются заново. Старый capture сохраняет своё прежнее дерево.
--refresh-cache обновляет данные **выбранного** журнала, не обнаруживает новые
публикации и не двигает границу B. Read не меняет Telegram-сообщения/закреп.

## Целостность и вытеснение

При чтении каждого blob проверяются длина и сохранённый SHA-256. У CHUNK
дополнительно сверяется part_sha256 из capture/FILE_COMMIT; ядро также проверяет
хеш файла. Неверный blob удаляется из производного кэша и скачивается заново
в обычном режиме; offline получает cache miss. Синтаксически неверные metadata
и неверные CHUNK с сети не сохраняются. Полная семантика metadata проверяется
ядром перед публикацией capture index; некоторые структурно корректные, но
семантически неверные documents могут остаться в blob cache и продолжат давать
ошибку чтения. Они не создают корректного индекса сами по себе.

Hash snapshot проверяется при загрузке; повреждённый/неразбираемый snapshot
удаляется вместе с его records и строится заново из metadata. Вся SQLite-база
при ошибке не заменяется автоматически. Checksums рассчитаны на обнаружение
повреждения; cache принадлежит локальному пользователю, это не подпись данных.

Blobs вытесняются по порядку использования до указанного budget. Blob больше
budget не сохраняется, но онлайн-чтение может завершиться успешно. Уменьшение
лимита удаляет слишком большие/давно использованные blobs при открытии.
Сохраняются до 16 последних использованных capture indexes, их records удаляются
каскадно. Старые авторитетные capture-каталоги и удалённые данные не удаляются.

Лимит относится к сумме blob payload, не к размеру файла SQLite: индекс/records
и служебные страницы добавляют объём, освобождённые страницы SQLite могут
остаться в файле для повторного использования. Автоматического VACUUM нет.
Это локальное вытеснение кэша, не GC данных Telegram из задачи #9.

## Текущие границы

Текущий reader восстанавливает metadata в приватный временный каталог перед
открытием ядра. На тёплом кэше это локальный I/O без повторных downloads;
слияние операций/выбор версии пока выполняются заново в памяти на каждый CLI
запуск. SQL хранит индекс исходных записей и проверенный adapter, а не готовые
FUSE handles. Массовый импорт остаётся ограничен прежними лимитами metadata.
Проверка имени перед put пока использует отдельный сетевой preflight без кэша.

## Проверки

16 новых сквозных тестов между отдельными CLI процессами: холодный/тёплый
кэш, офлайн и cache miss, lazy CHUNK, refresh/no-cache, новый capture с новым
REMOVE и чтение старого дерева, bot/root namespaces, повреждение CHUNK/metadata/
индекса/SQLite, схема и permissions/symlinks, XDG/HOME, лимит blobs и параллельное
открытие. Всего 88 тестов; ASan/UBSan локально с detect_leaks=0 из-за ptrace.
Живой кэш пока не проверен пользователем. Следующий этап — read-only FUSE.

Основание SQLite API: [sqlite3_open_v2](https://www.sqlite.org/c3ref/open.html),
[транзакции](https://www.sqlite.org/lang_transaction.html).
