# Отчёт о совпадающем содержимом

`tgfs gc-plan` анализирует опубликованные версии в выбранном capture. Он
группирует непустые FILE_COMMIT по размеру и SHA-256, когда манифесты
ссылаются на разные наборы частей. Учитываются старые версии и файлы с
разными именами, UUID и схемами разбиения. Повтор того же operation_id
представлен первым исходным FILE_COMMIT. Отдельные CHUNK без манифеста
в отчёт не попадают.

```bash
./build/tgfs gc-plan "${tgfs_net[@]}" --capture ./capture-011
```

Для каждой группы скачиваются части каждой версии, проверяются ссылки,
размеры, SHA-256 отдельных частей и всего файла. При ошибке проверки
команда возвращает 1 и пишет причину в stderr. Успешный вывод JSON содержит
канал, UUID корня, boundary_id, статус покрытия scan и массив groups.
В каждой группе есть размер, SHA-256 и verified_commits с идентификаторами
commit_id, object_id, version_id и chunk_ids. Поле catalog_entries каждой
версии показывает пары parent_object_id и name из каталогов, достижимых
из корня. Имя относится к версии, которую выберет обычное чтение из этого
capture. Несколько имён одного файла перечисляются отдельно. Каталог
обходится один раз даже при нескольких путях к нему или цикле.

На верхнем уровне chunk_references показывает для каждой части из групп
все ID FILE_COMMIT из capture, в которых она указана. Сюда входят старые
версии и повторы одной операции. Список отражает ссылки манифестов,
а проверка содержимого относится к verified_commits.

## Прежние captures

Чтобы учесть сохранённый снимок, добавьте `--retain-capture DIRECTORY`.
Флаг можно повторять. Для каждого снимка требуется тот же канал, UUID корня
и start_id, а его boundary_id должен быть меньше текущего.

```bash
./build/tgfs gc-plan "${tgfs_net[@]}" --capture ./capture-011 \
    --retain-capture ./capture-008 --retain-capture ./capture-009
```

При этом scope получает значение provided_captures_only, а
retained_captures показывает путь, границу, статус покрытия и
commit_references каждого снимка. В commit_references входят все
FILE_COMMIT, которые ссылаются на CHUNK из текущих групп. Поле chunk_ids
показывает только пересечение с частями из этих групп. Поле catalog_entries
содержит имена, которые в данном старом снимке ведут к этой версии.
Исторический манифест учитывается и при пустом catalog_entries, и при
отсутствии записи CHUNK в старом журнале. При ошибке чтения или проверки
снимка команда завершится ошибкой. Сами данные исторических версий здесь
не скачиваются повторно.

## Незавершённые загрузки

Добавьте `--retain-intent DIRECTORY` для каждого приватного каталога
состояния `put` или `put --replace`. Флаг можно использовать вместе с
`--retain-capture`. Поле scope получит значение
provided_captures_and_intents_only, а retained_intents перечислит
переданные незавершённые загрузки того же канала.

- saved_chunk_ids — сохранённые ссылки из intent.json.
- manifest_chunk_ids — ссылки из сохранённого манифеста, когда он есть.
- observed_chunk_ids — все части из основного capture с теми же UUID
  объекта и версии. Сюда попадают части, ID которых не успели записать
  после потерянного ответа.
- observed_commit_ids — коммиты из основного capture с теми же UUID объекта
  и версии или UUID операции. Отдельно выводятся известные file_commit_id
  и base_commit_id из intent.json.

Известные ID сохраняются в отчёте даже за пределами capture. Данные
загрузки и staging для этой сверки не скачиваются. Готовый intent с фазой
complete пропускается. Если журнал операции есть, команда держит общую
блокировку при чтении intent и показывает journal_locked=true. Для старого
intent без журнала journal_locked=false. Ошибка чтения, занятая блокировка
или оставшийся временный файл intent останавливают отчёт.

## Открытые файлы монтирования

`tgfs mount --capture` принимает `--open-files-dir DIRECTORY`. Укажите новый
приватный каталог вне точки монтирования. Монтирование атомарно обновляет
open-files.json при открытии и закрытии файла. Каждый открытый дескриптор
хранит исходный commit_id и все chunk_ids читаемой им версии. При ошибке
публикации ссылок открытие возвращает ошибку. Штатное размонтирование
оставляет пустой список. После аварийного завершения в отчёте могут
остаться ссылки уже закрытого процесса.

```bash
./build/tgfs mount "${tgfs_net[@]}" --capture ./capture-010 \
    --mountpoint "$HOME/mnt/tgfs" --open-files-dir "$HOME/.local/state/tgfs/mount-010"

./build/tgfs gc-plan "${tgfs_net[@]}" --capture ./capture-011 \
    --retain-open-files "$HOME/.local/state/tgfs/mount-010"
```

`--retain-open-files` можно повторять. Команда сверяет канал, корень и start_id,
проверяет границу монтирования и формат ID. Отчёт retained_open_files показывает
все записанные ссылки, включая файлы вне групп дубликатов. При наличии флага
scope равен provided_captures_and_local_state_only. Список отражает момент чтения
файла отчёта. Будущему удалению потребуется координация со всеми монтированиями,
включая открытие файлов после построения отчёта.

## Навигационные ссылки

Поле navigation_references есть в основном отчёте и у каждого старого
capture. Оно показывает входящие next_message на части из проверенных
групп. Каждая запись содержит source_message_id, source_type и chunk_id.
Учитываются SUPERBLOCK и записи журнала. Ссылка из старого снимка
учитывается и тогда, когда запись самой части в нём пропущена.

Команда собирает непосредственно наблюдаемые ссылки. Она не следует
за ними, поэтому цикл перечисляется как отдельные ссылки и не вызывает
дополнительных запросов. Отчёт ограничен входящими ссылками на CHUNK
из текущих групп дубликатов.

## Причины сохранения частей

В chunk_references у каждой части из проверенных групп появляется
retention_reasons. Причина указывается один раз, даже если она подтверждена
несколькими файлами или снимками.

| Причина | Основание |
| --- | --- |
| manifest_in_capture | Ссылка из FILE_COMMIT основного capture, включая исторические версии и повторные публикации. |
| visible_in_current_capture | Ссылка из проверенной версии, которую выбирает хотя бы одно имя в дереве основного capture. |
| retained_capture | Ссылка из манифеста переданного старого capture. |
| unfinished_put | Ссылка из незавершённой загрузки, в том числе через base_commit_id, когда этот манифест есть в основном capture. |
| open_file | Ссылка из явно переданного отчёта монтирования. |
| navigation_in_capture | Входящий next_message из основного capture. |
| navigation_in_retained_capture | Входящий next_message из переданного старого capture. |

Исторические манифесты учитываются наравне с текущими. Эти причины описывают
ссылки в переданных входных данных. Политика срока хранения и полномочия
на физическое удаление определяются отдельно.

## Предпросмотр лимита истории

```bash
./build/tgfs gc-plan "${tgfs_net[@]}" --capture ./capture-011 --keep-history 2
```

`--keep-history N` моделирует сохранение последней версии и N более
старых версий каждого объекта. Порядок задаётся ID первого FILE_COMMIT
операции. Повтор с тем же operation_id наследует место исходной публикации.
Пустая версия учитывается при подсчёте, а последняя версия сохраняется
даже у объекта без имени.

В chunk_references появляется history_preview. Поля within_limit_commit_ids
и outside_limit_commit_ids показывают, по какую сторону лимита находится
каждый манифест, ссылающийся на часть. retained_in_preview равно true, если
есть хотя бы один манифест в пределах лимита или отдельная причина сохранить
часть, например старый capture, открытый файл, intent или входящая
навигационная ссылка. Исходные retention_reasons остаются доступны.

Флаг действует только для текущего отчёта и только для частей проверенных
групп. false означает, что при выбранном лимите среди учтённых ссылок не
нашлось причины сохранить часть. Перед удалением нужны согласованная
политика хранения, проверка полноты данных и координация читателей и writer.

## Локальная блокировка тома

Для взаимного исключения на одной машине укажите существующий приватный
каталог через глобальный `--volume-lock DIRECTORY` перед командой.
Выберите один каталог на том и используйте его во всех процессах, которые
читают том, записывают данные или обслуживают его. Каталог должен быть
доступен тому же пользователю и находиться вне точки монтирования.

```bash
install -d -m 700 "$HOME/.local/state/tgfs/test-volume-lock"
./build/tgfs --volume-lock "$HOME/.local/state/tgfs/test-volume-lock" \
    gc-plan "${tgfs_net[@]}" --capture ./capture-011 --keep-history 2
```

gc-plan запрашивает эксклюзивную блокировку. Остальные команды берут
общую блокировку на весь срок работы. Монтирование удерживает её
до размонтирования, включая промежутки между открытиями файлов.
Если блокировка занята несовместимым режимом, команда завершается с кодом 1
до чтения или изменения тома. Несколько обычных команд могут работать
одновременно.

Блокировка действует на один и тот же каталог на локальной машине.
Её учитывают процессы, запущенные с этим флагом. Во время работы
сохраняйте сам каталог на месте. Для физического удаления нужны также
проверка всех источников ссылок и координация с другими машинами.

Пустой массив groups означает, что
в этом capture не нашлось совпадающих полных комплектов с разными ссылками.

Это инвентаризация для задачи [#9](https://github.com/Hanan4ik/tgfs/issues/9).
Команда читает capture и документы через getChat/getFile, без удаления,
публикации и записи в постоянный кэш. Одинаковое содержимое может быть
доступно под несколькими именами, относиться к сохраняемой истории или
использовать общие части. Отчёт ограничен выбранной границей и не выдаёт
разрешение на удаление. Для физической очистки ещё нужны правила
сохранения истории и навигационных ссылок, проверка полноты списка captures,
intents и монтирований и координация с чтением и записью.
