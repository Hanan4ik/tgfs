# F01. Две машины одновременно инициализируют один канал

## Постановка проблемы

Обе машины не находят готовый SUPERBLOCK, создают разные root_object_id и публикуют по заголовку. Разные mount могут выбрать разные корни одного канала. Запрет одновременного init уже оговорён, но технический способ его обеспечить не определён.

## Решение проблемы

### Решения пока нет

Определить обнаружение конкурирующих заголовков и правило выбора/отказа. Проверка перед отправкой не является атомарной блокировкой. Не вводить автоматически внешний координатор.

**Как проверить:** Запустить два init с одинаковым исходным состоянием; ни одна машина не должна молча объявить другой корень того же тома.

**Связи:** [SUPERBLOCK_V1](SUPERBLOCK_V1.md), [decisions/0003-journal-discovery](decisions/0003-journal-discovery.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F02. Telegram принял временный заголовок, но ответ init потерялся

## Постановка проблемы

После send временное сообщение может уже существовать, а его message_id не сохранён. Повторный init создаст лишнюю запись; автоматический новый UUID может создать второй корень. UUID объекта сам по себе не решает неизвестный результат доставки.

## Решение проблемы

### Есть идея

До send сохранять UUID и intent инициализации; предусмотреть поиск/сверку незавершённой попытки и явный resume. Формат временной записи, её адресация при потерянном ответе и алгоритм поиска пока не выбраны.

**Как проверить:** Оборвать ответ сразу после приёма send сервером и перезапустить процесс без известного ID временного сообщения.

**Связи:** [SUPERBLOCK_V1](SUPERBLOCK_V1.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F03. Падение между записью SUPERBLOCK, закреплением и локальным подтверждением

## Постановка проблемы

Окончательный заголовок мог быть записан, но ещё не закреплён, либо закреп уже установлен, а профиль/intent не обновлён. На следующем запуске нельзя приравнять это к отсутствию тома.

## Решение проблемы

### Правило принято, проверка не выполнена

Не форматировать при mount и не создавать новый корень автоматически. Нужна таблица стадий init, сверка исходного текста/закрепа и продолжение той же операции. Детали durable-переходов и потерянных ответов edit/pin ещё не реализованы.

**Как проверить:** Прервать init после каждого удалённого и локального шага; повтор не должен заменить уже созданный root_object_id.

**Связи:** [SUPERBLOCK_V1](SUPERBLOCK_V1.md), [PROTOCOL](PROTOCOL.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F04. Закреп снят, заменён или утрачен вместе с резервным locator

## Постановка проблемы

getChat может не дать нужный заголовок. Сохранённый superblock_message_id — принятый резервный путь, но новая машина может не иметь ни locator, ни подходящего pin.

## Решение проблемы

### Есть идея

Сначала использовать резервный ID и проверять тип/источник заголовка. Для полной потери locator определить recovery-конфигурацию или ручное указание ID; автоматический поиск начала через Bot API-only пока не гарантирован.

**Как проверить:** Проверить чужой pin, снятый pin, неправильный locator и чистую машину без обоих способов адресации.

**Связи:** [SUPERBLOCK_V1](SUPERBLOCK_V1.md), [PROTOCOL](PROTOCOL.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#6](https://github.com/Hanan4ik/tgfs/issues/6).

# F05. Профиль указывает другой канал или старый индекс относится к другому корню

## Постановка проблемы

channel_id хранится локально, а одинаковое имя профиля может указывать на иной том. После явной переинициализации того же канала root_object_id также может измениться. Старый index.sqlite3 способен показать неверные объекты.

## Решение проблемы

### Очевидное действие

Сверять фактический исходный канал, SUPERBLOCK и сохранённый root_object_id; при несовпадении останавливать использование индекса. Не сбрасывать автоматически dirty staging. UX явного переподключения/переинициализации ещё нужен.

**Как проверить:** Подменить channel_id, root_object_id и locator по отдельности; старые данные не должны смешиваться с новым томом.

**Связи:** [SUPERBLOCK_V1](SUPERBLOCK_V1.md), [CONFIGURATION](CONFIGURATION.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#4](https://github.com/Hanan4ik/tgfs/issues/4), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F06. Нет права отправить SCAN_MARKER и узнать свежую границу

## Постановка проблемы

Файловая система может быть read-only, а учётная запись при этом не иметь права писать в исходный канал. Принятая схема свежей границы требует отправки маркера; известный старый ID не доказывает актуальность канала.

## Решение проблемы

### Решения пока нет

Определить отдельный режим чтения до известной границы либо иной источник свежего конца. Не выдавать старое состояние за актуальное и не считать getUpdates постоянным независимым журналом для всех машин.

**Как проверить:** Смонтировать без права публикации при наличии более новых записей; статус свежести должен быть явным.

**Связи:** [PROTOCOL](PROTOCOL.md), [decisions/0003-journal-discovery](decisions/0003-journal-discovery.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#8](https://github.com/Hanan4ik/tgfs/issues/8).

# F07. Чтение через пересылку недоступно или неоднозначно по происхождению

## Постановка проблемы

Protected content, потеря прав или неподходящий служебный чат могут блокировать forwardMessage. Для поста, который сам является пересылкой, нельзя без проверки эксперимента приравнивать forward_origin к запрошенному каналу и ID; ID служебной копии также не является ID оригинала.

## Решение проблемы

### Есть идея

Сохранять исходную пару channel_id/message_id запроса, проверять допустимые варианты происхождения и capabilities до mount. Определить поддержку исходных пересланных постов и отказ при неподдержанном режиме; проверка на живом канале открыта.

**Как проверить:** Обычный пост, пересланный пост, protected content, другой бот и потеря доступа к служебному чату.

**Связи:** [TELEGRAM](TELEGRAM.md), [PROTOCOL](PROTOCOL.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#6](https://github.com/Hanan4ik/tgfs/issues/6).

# F08. Пропуск ID ошибочно принят за отсутствие данных

## Постановка проблемы

В диапазоне есть удалённые/служебные и посторонние сообщения, но timeout, 429 и отказ доступа могут выглядеть как неудачное чтение. Продвинув позицию сканирования через неопределённый ID, машина пропустит существующий commit. Потерянный ответ SCAN_MARKER также может оставить экземпляр без известной верхней границы.

## Решение проблемы

### Правило принято, проверка не выполнена

Не превращать сетевую ошибку в отсутствие сообщения. Нужна классификация ответов, интервалы проверенного покрытия и повтор неопределённых ID. Точные коды и основания окончательного пропуска ещё проверяются. При неизвестном ID маркера определить безопасный повтор получения новой границы; не считать случайный последний прочитанный ID завершением синхронизации.

**Как проверить:** Смешать настоящие пропуски и ошибки сети/прав; полный индекс должен совпасть с эталоном после восстановления доступа.

**Связи:** [PROTOCOL](PROTOCOL.md), [decisions/0003-journal-discovery](decisions/0003-journal-discovery.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F09. Разрыв, неверная цель или перескок next_message скрывают хвост

## Постановка проблемы

Процесс может отправить сообщение и упасть до связывания с предыдущим. Ссылка также может указывать назад, на удалённый/чужой объект либо перескочить незамеченную запись. null не доказывает конец.

## Решение проблемы

### Правило принято, проверка не выполнена

Граница задаётся маркером, а непроверенные интервалы сканируются по ID. Проверять цель и принадлежность, ограничивать обход и восстанавливать соседние связи по возможности. Принцип выбран; полный алгоритм покрытия и repairs ещё не реализован.

**Как проверить:** Обрыв перед link, цикл/ссылка назад, удалённая цель и скрытый промежуточный commit; сравнить с полным сканированием до той же B.

**Связи:** [PROTOCOL](PROTOCOL.md), [decisions/0003-journal-discovery](decisions/0003-journal-discovery.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F10. Обновления next_message и file_commit_id затирают друг друга

## Постановка проблемы

Два процесса читают старый caption: один меняет next_message, другой file_commit_id. Позднее редактирование всей строки возвращает устаревшее значение другого поля. Дополнительное чтение перед edit не устраняет окно гонки.

## Решение проблемы

### Есть идея

Считать обе ссылки восстанавливаемой оболочкой, сериализовать локальные edits и иметь идемпотентный repair по журналу. Межмашинного CAS нет; строгая схема сохранения обоих полей при гонках пока не определена.

**Как проверить:** Управляемо переставить два editMessageCaption; после repair должны сохраниться правильная навигация и backlink без изменения хешей/диапазонов.

**Связи:** [CHUNK_V1](CHUNK_V1.md), [decisions/0003-journal-discovery](decisions/0003-journal-discovery.md); [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F11. Один writer не может редактировать сообщения другого

## Постановка проблемы

Ремонт цепочки или backlinks требует изменения существующих text/caption. При разных ботах, правах и авторах конкретные редактирования могут быть недоступны; повторять отказ как временную ошибку бессмысленно.

## Решение проблемы

### Есть идея

Экспериментально определить поддерживаемую модель ботов/прав. Сканирование и прямые refs должны сохранять чтение без успешного repair; эксплуатационные ограничения записи и дальнейший режим при постоянном запрете ещё выбрать.

**Как проверить:** Два экземпляра одного бота и два разных бота с разными правами; запрет edit не должен ложно подтверждать repair.

**Связи:** [CHUNK_V1](CHUNK_V1.md), [decisions/0003-journal-discovery](decisions/0003-journal-discovery.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#6](https://github.com/Hanan4ik/tgfs/issues/6).

# F12. file_commit_id не заполнен после уже состоявшейся публикации

## Постановка проблемы

Commit отправлен, затем машина упала до обновления части или всех captions. Можно ошибочно признать file_commit_id=null доказательством незавершённости и удалить опубликованные байты.

## Решение проблемы

### Правило принято, проверка не выполнена

Публикация определяется FILE_COMMIT и его прямыми refs. Null не доказывает отсутствие commit. Восстановитель сверяет операцию и дописывает канонический ID; реализация и тесты частичного заполнения открыты.

**Как проверить:** Остановить writer после commit и после обновления каждого caption; файл должен читаться через прямой список частей.

**Связи:** [CHUNK_V1](CHUNK_V1.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md); [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#9](https://github.com/Hanan4ik/tgfs/issues/9).

# F13. Обратная ссылка ведёт к чужой версии или принимается за полный индекс ссылок

## Постановка проблемы

file_commit_id может указывать на другой объект/версию либо commit, в котором нет данного message_id. При переиспользовании части одним указателем нельзя перечислить все публикации, удерживающие её.

## Решение проблемы

### Очевидное действие

Проверять тип, object_id/version_id, размер/хеш и включение исходного ID части в refs. Backlink — не доказательство безопасности удаления; полный учёт достижимости и политика переиспользования ещё проектируются.

**Как проверить:** Неверный объект, версия, невыбранный физический дубль и несколько refs на один объект хранения.

**Связи:** [CHUNK_V1](CHUNK_V1.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md); [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#9](https://github.com/Hanan4ik/tgfs/issues/9).

# F14. Рост канала делает восстановление и repairs слишком медленными

## Постановка проблемы

Маркеры, неудачные отправки, чужие посты и удалённые сообщения расширяют диапазон ID. На чистой машине next_message не доказывает полноту непроверенных промежутков, поэтому безопасный обход может остаться линейным.

## Решение проблемы

### Есть идея

Локальный индекс проверенных интервалов уже предусмотрен. Нужен согласованный удалённый checkpoint/индекс с доказанной полнотой и правилами обновления/сжатия; формат и безопасное сокращение истории не выбраны.

**Как проверить:** Сравнить время и число запросов на длинном разреженном диапазоне с индексом и без него; ускорение не должно терять commit.

**Связи:** [PROTOCOL](PROTOCOL.md), [decisions/0003-journal-discovery](decisions/0003-journal-discovery.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#8](https://github.com/Hanan4ik/tgfs/issues/8).

# F15. Лимиты публичного API и длина записи достигнуты ровно на границе

## Постановка проблемы

Рабочий размер CHUNK — 20971520 байт, но реальная цепочка upload/getFile/download на границе ещё не проверена. Увеличение ID в изменяемых полях может удлинить caption; форматирование, добавленные поля или встроенные служебные байты тоже меняют размер.

## Решение проблемы

### Очевидное действие

Проверять размер документа и сериализованной оболочки до send/edit. Испытать C-1/C/C+1 и максимальные поддерживаемые ID; при изменении упаковки учитывать реальные байты. До эксперимента не объявлять endpoint проверенным.

**Как проверить:** Граничные размеры, длинный caption и его расширение после file_commit_id/next_message; ошибка не должна обрезать запись.

**Связи:** [CHUNK_V1](CHUNK_V1.md), [TELEGRAM](TELEGRAM.md); [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#6](https://github.com/Hanan4ik/tgfs/issues/6).

# F16. Список частей не помещается в FILE_COMMIT

## Постановка проблемы

Небольшой inline parts рассмотрен, но при большом файле текст станет слишком длинным. Несвязанные куски одного commit или обрезанный список не обеспечивают однозначную публикацию. Внешний манифест, если его ввести, тоже может отсутствовать, иметь неверный размер/хеш или неполный список.

## Решение проблемы

### Есть идея

Вынести список в document-манифест со ссылкой, размером и хешем в commit. Открыты схема, предел одного манифеста, разделение ещё более крупного списка и согласованность зависимостей. До этого отклонять неподдерживаемый размер, а не публиковать усечённый список.

**Как проверить:** Найти предел inline и проверить переход к внешнему манифесту, потерю/повреждение манифеста и превышение его лимита скачивания.

**Связи:** [FILE_COMMIT_V1](FILE_COMMIT_V1.md), [PROTOCOL](PROTOCOL.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#6](https://github.com/Hanan4ik/tgfs/issues/6).

# F17. Исходный файл меняется во время хеширования или загрузки

## Постановка проблемы

Хеш рассчитан для одних байтов, а диапазоны позже прочитаны из уже изменённого файла. Отправитель способен создать несовместимый комплект даже при корректной сети.

## Решение проблемы

### Есть идея

Заморозить версию в устойчивом staging, затем хешировать и загружать её. Выбрать блокирование записи, копию либо snapshot; определить требуемое место и поведение concurrent write. Новый write не должен менять байты уже подготовленной операции.

**Как проверить:** Менять исходный файл между хешем и каждой отправкой; опубликованные bytes должны соответствовать одной зафиксированной версии.

**Связи:** [CHUNK_V1](CHUNK_V1.md), [ARCHITECTURE](ARCHITECTURE.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md); [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F18. Загрузка оборвалась до FILE_COMMIT

## Постановка проблемы

В канале есть часть либо весь набор документов, но нет завершённой публикации. После restart неизвестно, какие upload уже состоялись и что можно повторно использовать/очистить.

## Решение проблемы

### Правило принято, проверка не выполнена

Без commit новая версия не видима. По durable intent восстанавливать ту же операцию и известные refs; неизвестные объекты не удалять автоматически. Формат intent, resume и срок хранения незавершённых загрузок ещё нужны.

**Как проверить:** Падение после каждой части и после последней части до commit; старое содержимое остаётся текущим.

**Связи:** [PROTOCOL](PROTOCOL.md), [CHUNK_V1](CHUNK_V1.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#9](https://github.com/Hanan4ik/tgfs/issues/9).

# F19. Ответ sendDocument потерялся и появился физический дубль

## Постановка проблемы

Документ мог попасть в канал, но его ID/file_id неизвестны writer. Повтор создаёт второй экземпляр части. Совпадение имени или file_commit_id=null не доказывает, какой из них лишний.

## Решение проблемы

### Есть идея

Сохранять известные ответы, распознавать candidates по метаданным/диапазонам и публиковать точный выбранный комплект. Обнаружение неизвестного дубля и безопасная очистка после потерянного ответа ещё не спроектированы полностью.

**Как проверить:** Потерять ответ upload, повторить его и восстановиться без первоначального ID; один набор refs не должен превратиться в две последовательные части.

**Связи:** [CHUNK_V1](CHUNK_V1.md), [PROTOCOL](PROTOCOL.md); [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#9](https://github.com/Hanan4ik/tgfs/issues/9).

# F20. Ответ FILE_COMMIT потерялся и retry ошибочно повышает приоритет старой версии

## Постановка проблемы

Возможна последовательность A/120, B/125, повтор A/130. Принято учитывать первую корректную публикацию операции, но локальная реализация должна найти её и не переключить файл обратно на A.

## Решение проблемы

### Правило принято, проверка не выполнена

Устойчиво сохранять operation_id до send; у одинаковой операции использовать минимальный исходный ID, затем сравнивать разные операции. Открыты точный replay, поиск первого commit при потерянном ответе и интеграция с intents.

**Как проверить:** Проверить обе ветки: A/120 существовал — выигрывает B/125; A/120 не существовал — первая A/130 может выиграть.

**Связи:** [PROTOCOL](PROTOCOL.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F21. Один operation_id встретился с разными содержательными полями

## Постановка проблемы

Из-за ошибки resume, клонирования локального журнала или подмены записи под одним ID могут появиться разные refs, версии или размеры. Простое правило «первый» способно скрыть нарушение протокола.

## Решение проблемы

### Есть идея

Ошибка уже должна диагностироваться. Нужно утвердить точную нормализацию/сравнение JSON, исключение изменяемой оболочки и последствия: отказ операции, остановка replay или изоляция записи. Не объявлять семантически разные операции обычными дублями.

**Как проверить:** Одинаковый JSON с разными пробелами и next_message; затем изменённые refs/хеши под тем же operation_id.

**Связи:** [PROTOCOL](PROTOCOL.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F22. Commit прочитаны не по порядку или сканирование остановлено до раннего повтора

## Постановка проблемы

Первый найденный commit операции не обязательно имеет минимальный ID. Если индекс объявлен актуальным до проверки предыдущих интервалов, текущая версия может отличаться на машинах.

## Решение проблемы

### Правило принято, проверка не выполнена

Хранить канонический минимум и проверенное покрытие, пересчитывать выбор при обнаружении ранней записи. Нужен точный критерий завершённости replay до B и поведения mount, пока часть диапазона неизвестна.

**Как проверить:** Разный порядок доставки 120/125/130 и обрыв в промежутке; после полного покрытия итоговые индексы совпадают.

**Связи:** [PROTOCOL](PROTOCOL.md), [decisions/0003-journal-discovery](decisions/0003-journal-discovery.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#8](https://github.com/Hanan4ik/tgfs/issues/8).

# F23. Удалён первый commit операции, а его поздний повтор остался

## Постановка проблемы

После удаления канонической записи повтор может стать «первым» и получить более поздний приоритет. Старое содержимое способно вновь перекрыть новую операцию.

## Решение проблемы

### Решения пока нет

Запрет небезопасного удаления уже оговорён. Для сокращения истории нужен согласованный checkpoint или реестр исходного канонического ID и правило доверия ему. До этого не считать commit обычным удаляемым дублем.

**Как проверить:** Удалить 120 из A/120, B/125, A/130 в модели истории; подтверждённый порядок операций не должен самопроизвольно измениться.

**Связи:** [PROTOCOL](PROTOCOL.md), [CHUNK_V1](CHUNK_V1.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#9](https://github.com/Hanan4ik/tgfs/issues/9).

# F24. Смешаны версии, повторные комплекты или разные схемы разбиения

## Постановка проблемы

Несколько загрузок одинаковых байтов могут перемешиваться; при другом размере частей одноимённые номера означают другие диапазоны. Комплект, выбранный по имени/object_id без версии и refs, может оказаться неверным.

## Решение проблемы

### Есть идея

Для опубликованной версии использовать точные refs и проверки диапазонов/хешей. Первый полный проверенный альтернативный комплект допустим по принятому принципу; алгоритм поиска альтернатив без комбинаторного перебора и условия совместимости ещё не выбраны.

**Как проверить:** Два полных дубля, неполный дубль, перемешивание и разное разбиение при одинаковом общем hash/size.

**Связи:** [CHUNK_V1](CHUNK_V1.md), [PROTOCOL](PROTOCOL.md); [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#9](https://github.com/Hanan4ik/tgfs/issues/9).

# F25. Размер части в локальном конфиге изменился после публикации

## Постановка проблемы

Новая машина может иметь другой chunk_size_bytes. Если она вычислит старые offsets/part_count по своей настройке, то неверно проверит или соберёт существующую версию.

## Решение проблемы

### Есть идея

Реальные диапазоны брать из удалённой версии/манифеста, а не переинтерпретировать их по текущему default. Уточнить, фиксируется ли C на версию явно и какие схемы разбиения совместимы с caption.

**Как проверить:** Загрузить с одним C, восстановить с меньшим C в профиле; старые bytes и refs остаются корректными.

**Связи:** [CHUNK_V1](CHUNK_V1.md), [CONFIGURATION](CONFIGURATION.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F26. Имя document отсутствует или имеет некорректный суффикс

## Постановка проблемы

Принято имя `<исходное_имя>.<номер_части>`: последняя точка отделяет индекс, остальное — полное имя, включая расширение. part_index в caption отсутствует. Из корректного video.mp4.0 имя извлекается однозначно. Открытый риск — потеря или изменение document.file_name при работе API; без корректного имени этот источник метаданных недоступен.

## Решение проблемы

### Есть идея

Правило разбора принято и записано в CHUNK_V1.md: непустое исходное имя, последний суффикс из ASCII-цифр без знака и ведущих нулей, индекс от 0 до part_count-1 с проверкой переполнения. Некорректное или отсутствующее имя считается ошибкой метаданных. Идея проверки: подтвердить сохранность filename в фактических upload/пересылках, включая длинные и Unicode-имена; результаты экспериментов пока отсутствуют.

**Как проверить:** Загрузка/пересылка длинных и Unicode-имён, rename в TGFS, отсутствие имени, некорректный суффикс и несоответствие индекса диапазону offset.

**Связи:** [CHUNK_V1](CHUNK_V1.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md); [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#6](https://github.com/Hanan4ik/tgfs/issues/6).

# F27. Опубликованная часть отсутствует либо не проходит проверку

## Постановка проблемы

Документ мог быть удалён/недоступен, ссылка неверна либо скачанные bytes повреждены. Наличие commit само по себе не обеспечивает доступность всех зависимостей.

## Решение проблемы

### Очевидное действие

Не возвращать неполные данные как корректный файл и не подменять отсутствующие bytes нулями. Проверять part_sha256/size, различать постоянную потерю и временную ошибку. Конкретные retry, errno и разрешённый поиск альтернативного комплекта ещё уточняются.

**Как проверить:** Пропавшая часть, другой document по ref, неверный offset/size/hash и восстановление после временной недоступности.

**Связи:** [CHUNK_V1](CHUNK_V1.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md), [ARCHITECTURE](ARCHITECTURE.md); [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F28. Повреждён локальный кэш или параллельные чтения используют непроверенный объект

## Постановка проблемы

Часть может быть испорчена на диске, отнесена к неверному ключу или видна до завершения скачивания. Два read могут одновременно писать один cache-файл или исчерпать место повторными загрузками.

## Решение проблемы

### Есть идея

Кэшировать по неизменяемой идентичности содержимого/версии и диапазону, проверять bytes, атомарно публиковать готовый cache-файл и объединять ожидание одной загрузки. Лимиты, LRU и синхронизация ещё не реализованы.

**Как проверить:** Подменить cache-файл, выполнить два read одного диапазона, оборвать download и повторить после remount.

**Связи:** [ARCHITECTURE](ARCHITECTURE.md), [CHUNK_V1](CHUNK_V1.md); [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#8](https://github.com/Hanan4ik/tgfs/issues/8).

# F29. Пустая версия перепутана с отсутствующей частью или неправильной оболочкой

## Постановка проблемы

Пустой файл представлен текстовым commit без document. Отсутствующий caption у CHUNK или parts=[] у непустой версии не должны восприниматься как допустимый пустой файл.

## Решение проблемы

### Правило принято, проверка не выполнена

Проверять тип сообщения, magic/type и совместимость оболочки. Для пустой версии требуются size=0, нулевое количество, пустые refs и хеш пустых bytes. Нужны единый validator, точная схема и проверка крайних случаев разбиения.

**Как проверить:** 0, 1, C-1, C, C+1, 2C, 2C+1; CHUNK без caption, пустой commit с ненулевым размером и лишний пустой хвост.

**Связи:** [CHUNK_V1](CHUNK_V1.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F30. JSON или числа приводят к переполнению, расходу памяти или неоднозначному разбору

## Постановка проблемы

Одинаковые ключи, неверные типы, huge part_count, offset+size с переполнением, отрицательные числа и чрезмерная вложенность могут повредить C-парсер или породить разные трактовки записи.

## Решение проблемы

### Очевидное действие

Проверять размер до разбора, типы, UUID/hex, числовой диапазон и арифметику, длину/покрытие списка; не исполнять метаданные. Неизвестную версию формата не монтировать как известную. Конкретные бюджеты parser и политика неизвестных полей ещё открыты.

**Как проверить:** Набор malformed JSON, числовые границы, чрезмерные списки и неподдерживаемая версия; ограниченные память/время без частичного применения.

**Связи:** [SUPERBLOCK_V1](SUPERBLOCK_V1.md), [CHUNK_V1](CHUNK_V1.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F31. Генератор UUID или восстановление ID дали повтор/подмену идентичности

## Постановка проблемы

Для object_id выбран UUIDv4, но ошибка случайности не должна приводить к timestamp-fallback. operation_id/version_id и точная обработка совпадающего ID разных объектов ещё не полностью согласованы; retry с заново сгенерированным ID ломает идемпотентность.

## Решение проблемы

### Есть идея

Использовать проверенный CSPRNG и устойчивое сохранение до send, не регенерировать существующие ID на машине 2. Выбрать генераторы оставшихся ID и действия при конфликтующих определениях. Тесты ошибок генератора и resume ещё нужны. Конкретная библиотека генерации ещё не выбрана.

**Как проверить:** Искусственный отказ случайности, заданные одинаковые UUID, потеря intent и восстановление известного объекта на другой машине.

**Связи:** [SUPERBLOCK_V1](SUPERBLOCK_V1.md), [PROTOCOL](PROTOCOL.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F32. Новое содержимое опубликовано, но имя файла не создано атомарно

## Постановка проблемы

Текущий FILE_COMMIT описывает известный объект. При первом создании отдельная публикация имени и содержимого может оставить недостижимый объект либо видимое имя без готовой версии.

## Решение проблемы

### Есть идея

Предложено create_entry с parent_object_id/name в первом FILE_COMMIT; последующие изменения содержимого не должны возвращать старое имя. Это ещё не принято: нужны точная схема, тип операции и правила replay.

**Как проверить:** Падение между каждым шагом создания; нельзя показывать недогруженный файл и нельзя потерять успешно опубликованное имя.

**Связи:** [FILE_COMMIT_V1](FILE_COMMIT_V1.md), [PROTOCOL](PROTOCOL.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F33. Разные машины создали разные object_id по одному пути

## Постановка проблемы

Обе машины создают /documents/video.mp4, но UUID объектов различаются. Принятое правило последней версии одного object_id не выбирает, какой объект занимает одно имя родителя.

## Решение проблемы

### Решения пока нет

Отдельно определить конфликт directory entry: отказ, порядок операций, замена либо сохранение альтернатив. Не переносить правило содержимого на пространство имён без согласования; проверить create и overwrite существующего пути.

**Как проверить:** Два create одного имени, создание после удаления и конфликт каталога с обычным файлом.

**Связи:** [PROTOCOL](PROTOCOL.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F34. Каталог отсутствует, удалён или образует цикл родителей

## Постановка проблемы

Операция создания дочернего имени может ссылаться на неизвестный parent, файл вместо каталога либо каталог, удалённый другой машиной. Перемещение может создать цикл и сделать обход бесконечным.

## Решение проблемы

### Есть идея

Утвердить операции создания каталога и проверки родительского графа. Для некорректных refs предусмотреть отказ/диагностику и лимиты обхода; поведение зависимых операций и появления родителя позднее ещё определить.

**Как проверить:** Отсутствующий parent, перемещение в собственного потомка, удаление родителя во время create и восстановление пустой папки.

**Связи:** [PROTOCOL](PROTOCOL.md), [SUPERBLOCK_V1](SUPERBLOCK_V1.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F35. Rename, replace и delete конфликтуют с параллельной записью

## Постановка проблемы

Одна машина переименовывает/удаляет объект, другая публикует его содержимое по устаревшему состоянию. Не определены атомарная замена назначения, повторное появление имени, удаление непустой папки и порядок таких операций.

## Решение проблемы

### Решения пока нет

Согласовать журнальные операции пространства имён, их идемпотентность и порядок. Общий object_id помогает связать изменения, но не является готовым решением. Устаревшая запись содержимого не должна случайно переиздавать прежнее имя.

**Как проверить:** Rename+write, unlink+write, rename поверх существующего файла и два rename одного объекта/назначения.

**Связи:** [PROTOCOL](PROTOCOL.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F36. Очистка удаляет часть, которую ещё читает другая машина

## Постановка проблемы

Открытый descriptor может держать старую версию после замены/unlink. Локальный счётчик читателей одной машины не сообщает о читателях другого экземпляра без координатора.

## Решение проблемы

### Решения пока нет

Выбрать гарантию удержания: период хранения, явные ограничения обслуживания, иной учёт читателей или отказ от автоматического удаления. Нельзя объявить безопасным удаление только потому, что текущая версия уже новая.

**Как проверить:** Машина A читает старую версию, B заменяет/удаляет имя, затем запускается cleanup; поведение должно соответствовать выбранной гарантии.

**Связи:** [ARCHITECTURE](ARCHITECTURE.md), [PROTOCOL](PROTOCOL.md), [CHUNK_V1](CHUNK_V1.md); [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#9](https://github.com/Hanan4ik/tgfs/issues/9).

# F37. Очистка дубликатов гоняется с новой публикацией

## Постановка проблемы

Между dry-run и delete другая машина может опубликовать refs на выбранный для удаления объект. Проверка «никто не использует» перед удалением не атомарна; backlink не перечисляет всех пользователей.

## Решение проблемы

### Решения пока нет

Нужен безопасный протокол обслуживания или явно остановленные writer с обеспечиваемым ограничением. До его принятия dry-run не является разрешением на concurrent GC; единственная проверенная копия не удаляется.

**Как проверить:** Публикация нового commit между вычислением кандидатов и delete, неполный дубль и повтор cleanup.

**Связи:** [PROTOCOL](PROTOCOL.md), [CHUNK_V1](CHUNK_V1.md); [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#9](https://github.com/Hanan4ik/tgfs/issues/9).

# F38. Удаление старых сообщений невозможно или выполнено лишь частично

## Постановка проблемы

Для выбранного Bot API документировано ограничение deleteMessage по возрасту/правам. Часть delete могла пройти до падения, либо ответ потерян; старые/недоступные дубликаты нельзя обещать очистить полностью.

## Решение проблемы

### Есть идея

Сохранять журнал конкретных ID, различать удалённое и неизвестное состояние, повторять безопасно и показывать неочищенные объекты. Не заменять backend без отдельного решения; учёт прогресса и компенсация неполного обслуживания ещё нужны.

**Как проверить:** До/после возрастной границы, отзыв прав, падение после первого delete и timeout после успешного удаления.

**Связи:** [TELEGRAM](TELEGRAM.md), [PROTOCOL](PROTOCOL.md); [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#9](https://github.com/Hanan4ik/tgfs/issues/9).

# F39. Удаление маркера или части разрушило навигационную цепочку

## Постановка проблемы

Даже доказанно лишний payload может быть звеном next_message. Удалив маркер/дубль, cleanup оставит ссылку на отсутствующее сообщение; параллельный repair может снова записать старый адрес.

## Решение проблемы

### Есть идея

Согласовать перенаправление ссылок, порядок удаления и repair при сбое. Пока держать fallback-сканирование и не удалять опорные записи вслепую. Строго безопасное обслуживание изменяемых ссылок при нескольких writer открыто.

**Как проверить:** Удаление среднего звена, потерянный ответ перенаправления и поздний edit от другой машины; восстановление не теряет хвост.

**Связи:** [CHUNK_V1](CHUNK_V1.md), [decisions/0003-journal-discovery](decisions/0003-journal-discovery.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#9](https://github.com/Hanan4ik/tgfs/issues/9).

# F40. Очистка state уничтожила единственную копию неопубликованных изменений

## Постановка проблемы

SQLite-индекс восстанавливаем, но intents/staging могут содержать данные, ещё не отправленные в Telegram. Повреждение индекса, очистка всей state-директории или потеря диска имеют разные последствия.

## Решение проблемы

### Очевидное действие

Разделять confirmed index, dirty intents/staging и чистый cache; не удалять dirty при rebuild и при несовпадении корня. Нужен конкретный recovery-процесс и описание границ гарантий: Telegram не восстановит никогда не загруженные bytes.

**Как проверить:** Повредить только индекс, удалить только cache, оборвать транзакцию intent и отдельно потерять staging; диагностика не выдаёт ложное удалённое сохранение.

**Связи:** [SUPERBLOCK_V1](SUPERBLOCK_V1.md), [ARCHITECTURE](ARCHITECTURE.md); [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#4](https://github.com/Hanan4ik/tgfs/issues/4), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F41. Локальный диск заполнен или процесс упал между fsync разных файлов

## Постановка проблемы

Запись staging, SQLite и каталогов диска не становится единой durable-транзакцией сама по себе. Большой файл/кэш способен исчерпать место; после crash refs/intents могут не соответствовать сохранённым bytes.

## Решение проблемы

### Есть идея

Определить точный порядок fsync staging/журнала/каталогов, атомарные переходы и бюджеты места. При ENOSPC сохранять dirty и не подтверждать фиксацию. Выбор staging целиком или по dirty chunks ещё открыт.

**Как проверить:** Падение после каждой локальной записи/fsync, ENOSPC на разных стадиях и превышение лимита cache.

**Связи:** [ARCHITECTURE](ARCHITECTURE.md), [CREATE_FILE_SCENARIO](CREATE_FILE_SCENARIO.md); [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F42. Два локальных mount или клонированный state конфликтуют в одном томе

## Постановка проблемы

Разные профили одного канала могут открыть один state без координации. Скопированный intent на другую машину способен продолжить ту же operation_id с иными локальными данными. Локальная блокировка не защищает от других хостов.

## Решение проблемы

### Есть идея

Выбрать владение локальным state и lock по идентичности тома, запретить несовместимое совместное использование индекса; распознавать повтор операции по неизменяемому описанию. Правила клонирования и resume с другого диска ещё нужны.

**Как проверить:** Два профиля одного канала, параллельный mount одного state и клонированный незавершённый intent.

**Связи:** [CONFIGURATION](CONFIGURATION.md), [SUPERBLOCK_V1](SUPERBLOCK_V1.md), [PROTOCOL](PROTOCOL.md); [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#4](https://github.com/Hanan4ik/tgfs/issues/4), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F43. Приложение получило успех записи, хотя удалённая фиксация неизвестна

## Постановка проблемы

write может завершиться в локальном staging, close/release не всегда подходят как единственный канал ошибки, а upload/commit ещё не завершён. Не утверждены точные обещания write/fsync/flush/release и fsync(parent).

## Решение проблемы

### Есть идея

Разделить локально принятые bytes и подтверждённую публикацию; неизвестный результат не маскировать успехом удалённого fsync. Утвердить таблицу гарантий и recovery при поздней ошибке/перезапуске.

**Как проверить:** write+close без fsync, fsync с timeout, ошибка после commit и шаблон редактора temp -> fsync -> rename -> fsync(parent).

**Связи:** [ARCHITECTURE](ARCHITECTURE.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md); [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F44. Чтение смешало версии или kernel/cache не узнал об изменении

## Постановка проблемы

После новой публикации один open может видеть часть старой и часть новой версии, если refs выбираются заново на каждом read. Статус snapshot mount, автообновление, inode lifetime и invalidation ещё не согласованы для журнала.

## Решение проблемы

### Есть идея

Привязывать handle к конкретной версии и определить обновление каталога/атрибутов. Прежняя идея фиксированного snapshot/remount — кандидат, а не уже проверенная гарантия. Не требовать одинаковых локальных inode между машинами.

**Как проверить:** Два read одного handle вокруг новой публикации, remount, смена длины файла и удаление/замена открытого имени.

**Связи:** [ARCHITECTURE](ARCHITECTURE.md), [FILE_COMMIT_V1](FILE_COMMIT_V1.md); [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#8](https://github.com/Hanan4ik/tgfs/issues/8).

# F45. Append, truncate и random write изменили не те bytes или потеряли dirty-данные

## Постановка проблемы

Для локального редактирования ещё не определены частичные изменения, расширение, обрезание, параллельные write одного inode и отделение новой записи от уже загружаемого snapshot.

## Решение проблемы

### Решения пока нет

Утвердить модель staging/заморозки и порядок локальных операций до нового commit. Если функция вне MVP — явно возвращать неподдерживаемую операцию, а не имитировать её успех.

**Как проверить:** Записи через границу части, truncate до 0/на границе, append во время upload и два writer одного локального файла.

**Связи:** [ARCHITECTURE](ARCHITECTURE.md), [CHUNK_V1](CHUNK_V1.md); [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F46. Сеть, offline и 429 превращают системный вызов в бесконечное ожидание

## Постановка проблемы

Повтор каждой операции без лимита удерживает FUSE-запросы и память очередей. Отмена/unmount может не остановить запрос; при offline могут ошибочно возвращаться нули либо старое состояние без отметки.

## Решение проблемы

### Есть идея

Определить timeout, retry_after, backoff, ограничения очередей и errno; читать offline только проверенные доступные bytes. Неизвестный результат send разбирать отдельно от явного отказа. Конкретная политика и отмена ещё не выбраны.

**Как проверить:** 429 с задержкой, сетевой обрыв, отмена read/upload, unmount во время ожидания и исчерпание очереди.

**Связи:** [ARCHITECTURE](ARCHITECTURE.md), [TELEGRAM](TELEGRAM.md); [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F47. Смена бота или отзыв прав сделали сохранённые file_id бесполезными

## Постановка проблемы

Локальные Telegram file_id привязаны к боту; после смены учётных данных или доступа к каналу прежний shortcut может не работать. Потеря прав во время операции отличается от временной сети.

## Решение проблемы

### Есть идея

Восстанавливать file_id через известные исходные refs при наличии прав и проверять capabilities. Не путать отсутствие доступа с удалением документа; определить reconnect, отказ mount и судьбу dirty staging. Смену токена того же бота отличать от смены самого бота: ошибка авторизации не доказывает непригодность file_id.

**Как проверить:** Другой бот, смена токена, отзыв прав посреди upload и восстановление из чистого индекса.

**Связи:** [PROTOCOL](PROTOCOL.md), [TELEGRAM](TELEGRAM.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#4](https://github.com/Hanan4ik/tgfs/issues/4), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F48. Профиль, XDG-пути, proxy или helper выбрали не те данные/секреты

## Постановка проблемы

Относительные пути, приоритет user/system, несколько профилей и overrides ещё проектируются. Ошибка может открыть чужой state, передать токен в argv/log или дать привилегированному helper доступ к неподходящему secret. Proxy/DNS также требуют выбранной HTTP-библиотеки.

## Решение проблемы

### Есть идея

Утвердить разрешение путей относительно профиля, явный scope, secret-файлы и безопасный набор options; валидировать до mount. Прокси до Bot API отделить от маршрута собственного сервера. Схема/реализация и тесты ещё не готовы.

**Как проверить:** Конфликт user/system, пути с обходом, два профиля одного канала, неверный proxy/DNS и проверка отсутствия токена в логах/аргументах.

**Связи:** [CONFIGURATION](CONFIGURATION.md); [#4](https://github.com/Hanan4ik/tgfs/issues/4), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F49. Неподдерживаемая Linux-операция выглядит успешной

## Постановка проблемы

Hardlink/symlink, mmap, xattr, locks, sparse, права/владельцы и времена не имеют завершённого контракта. Приложение может рассчитывать на поведение, которого TGFS не обеспечивает.

## Решение проблемы

### Решения пока нет

Для каждой операции выбрать поддержку, ограничение или явный errno. Не обещать POSIX-семантику только потому, что файл виден через FUSE. UID/GID/mode между машинами и допустимые имена также требуют точного правила.

**Как проверить:** Матрица вызовов и атрибутов, неподдерживаемые имена/типы, readonly write и приложение, использующее locks или temp+rename.

**Связи:** [ARCHITECTURE](ARCHITECTURE.md), [PROTOCOL](PROTOCOL.md); [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#8](https://github.com/Hanan4ik/tgfs/issues/8).

# F50. Внешнее изменение канала или утрата удалённых данных нарушили доверие

## Постановка проблемы

Администратор может удалить/изменить записи, а канал может стать недоступен целиком. Хеш проверяет bytes относительно метаданных, но не доказывает подлинность, если изменены и bytes, и хеш. Отдельной подписи/второй копии в принятой схеме нет.

## Решение проблемы

### Решения пока нет

Определить модель доверия и границы восстановления. Диагностировать повреждение и доступность, не выполнять тихий откат под видом текущей версии. Подписи, резервирование и восстановление из второй копии — только возможные отдельные решения, не текущие гарантии.

**Как проверить:** Удалённый commit/канал, подмена согласованных метаданных и потеря доступа; не обещать восстановить отсутствующие bytes из одних UUID.

**Связи:** [PROTOCOL](PROTOCOL.md), [CREATE_FILE_SCENARIO](CREATE_FILE_SCENARIO.md), [ARCHITECTURE](ARCHITECTURE.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#7](https://github.com/Hanan4ik/tgfs/issues/7).

# F51. Старый формат или непроверенный импорт трактуется как действующий TGFS

## Постановка проблемы

В репозитории сохранены исторические предложения полного каталога/fs_uuid/смены superblock и более новые журнальные схемы. Старый канал, запись другой версии или конфигурация 16 MiB не должны автоматически интерпретироваться по удобному черновику. Импорт до start_id ещё не определён.

## Решение проблемы

### Есть идея

Действующие решения брать из STATE, SUPERBLOCK/CHUNK/FILE_COMMIT и ADR-0003; исторические документы не возвращают старый координатор. Утвердить единую версию wire-format, миграцию/отказ, контроль согласованности и отдельный импорт без удаления чужих постов.

**Как проверить:** Смешанные версии/типы, старый каталог, обычный канал с историей до start_id и round-trip одного набора записей разными клиентами.

**Связи:** [STATE](STATE.md), [PROTOCOL](PROTOCOL.md), [REQUIREMENTS](REQUIREMENTS.md), [decisions/0003-journal-discovery](decisions/0003-journal-discovery.md); [#2](https://github.com/Hanan4ik/tgfs/issues/2), [#5](https://github.com/Hanan4ik/tgfs/issues/5), [#6](https://github.com/Hanan4ik/tgfs/issues/6), [#8](https://github.com/Hanan4ik/tgfs/issues/8).
