# Инициализация тестового тома

`tgfs init` реализует последовательность SUPERBLOCK_V1: локальный intent с
UUIDv4 → временный текст → editMessageText с настоящим ID → закрепление →
проверка getChat/pinned_message. Чужой закреп не заменяется. Команда проверяет
бота, канал и права администратора post/edit (для закрепления в канале).

Запускайте только один initializer на канал. `--new-volume` означает ваше
подтверждение, что в канале нет существующего TGFS-тома, включая незакреплённый
заголовок. Отсутствие pin само по себе этого не доказывает; полный поиск
предыдущих SUPERBLOCK и распределённая защита одновременного init пока отсутствуют.
Для тестового канала, содержащего только TGFS_PROBE, допустим такой запуск:

```bash
install -d -m 700 "$HOME/.local/state/tgfs"
./build/tgfs init --new-volume \
  --token-file "$HOME/.config/tgfs/secrets/test.token" \
  --storage-chat-id -1003916921678 \
  --state-dir "$HOME/.local/state/tgfs/test-init" \
  --proxy socks5h://127.0.0.1:10808
```

Родительский каталог state-dir должен существовать, сам state-dir — отсутствовать.
Токен и пароли в intent не сохраняются. Файл intent.json содержит storage_chat_id,
root_object_id, superblock_message_id и phase. Фазы: send_pending, edit_pending,
pin_pending, complete. Замена через intent.tmp/rename с fsync; UUID сохраняется
до первой отправки. Удалённый заголовок получает обязательный next_message=null.
Инициализация оставляет одно обычное сообщение в хранилище и закрепляет его;
Telegram также может создать служебную запись о закреплении. Probe-документы
не удаляются. Проверка pin непосредственно перед закреплением не является
атомарной блокировкой от второго initializer.

При ошибке сохраните каталог состояния. Повторный init с тем же state-dir
не отправляет новый заголовок. Автоматического resume нет: после неизвестного
ответа нужно сверить канал с intent, не удалять intent и не выбирать новый
state-dir для слепого повтора. send_pending может означать уже отправленное
сообщение с неизвестным ID; UUID находится во временном тексте. Ошибки
печатают известный message_id и outcome_unknown.

После успеха запустите scan (output должен отсутствовать):

```bash
./build/tgfs scan \
  --token-file "$HOME/.config/tgfs/secrets/test.token" \
  --storage-chat-id -1003916921678 \
  --service-chat-id -1004400939172 \
  --proxy socks5h://127.0.0.1:10808 \
  --output ./capture-001
```

При снятом pin сохранённый superblock_message_id можно передать scan через
--start-id. Непересылаемые служебные записи могут дать scan код 3 с
coverage_verified=false: такой результат не объявляется полным.

Локально проверены успех, UUID/ID, существующий pin, нехватка прав,
неизвестный ответ send и отсутствие повторной отправки с тем же intent.
Все 47 тестов и ASan/UBSan проходят (локально detect_leaks=0 из-за ptrace).
Живой init не выполнен: токен хранится у пользователя. Это инициализация
заголовка, а не готовая ФС; удалённое чтение и FUSE остаются следующим этапом.
