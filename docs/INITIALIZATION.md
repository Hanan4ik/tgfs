# Инициализация тестового тома

`tgfs init` реализует последовательность SUPERBLOCK_V1: локальный intent с
UUIDv4 → временный текст → editMessageText с настоящим ID → закрепление →
проверка getChat/pinned_message. Чужой закреп не заменяется. Команда проверяет
бота, канал и права администратора post/edit (для закрепления в канале).

Запускайте только один initializer на канал. `--new-volume` означает ваше
подтверждение, что в канале нет существующего TGFS-тома, включая незакреплённый
заголовок. Отсутствие pin само по себе этого не доказывает; полный поиск
предыдущих SUPERBLOCK и распределённая защита одновременного init пока отсутствуют.
Для тестового канала, содержащего только TGFS_PROBE, допустим такой запуск:

```bash
install -d -m 700 "$HOME/.local/state/tgfs"
./build/tgfs init --new-volume \
  --token-file "$HOME/.config/tgfs/secrets/test.token" \
  --storage-chat-id -1003916921678 \
  --state-dir "$HOME/.local/state/tgfs/test-init" \
  --proxy socks5h://127.0.0.1:10808
```

Родительский каталог state-dir должен существовать, сам state-dir — отсутствовать.
Токен и пароли в intent не сохраняются. Файл intent.json содержит storage_chat_id,
root_object_id, superblock_message_id и phase. Фазы: send_pending, send_rejected, edit_pending,
pin_ready, pin_pending, pin_rejected, complete. Замена через intent.tmp/rename с fsync; UUID сохраняется
до первой отправки. Удалённый заголовок получает обязательный next_message=null.
Инициализация оставляет одно обычное сообщение в хранилище и закрепляет его;
Telegram также может создать служебную запись о закреплении. Probe-документы
не удаляются. Проверка pin непосредственно перед закреплением не является
атомарной блокировкой от второго initializer.

При ошибке сохраните каталог состояния. Повторный init с тем же state-dir
не отправляет новый заголовок. После неизвестного
ответа нужно сверить канал с intent, не удалять intent и не выбирать новый
state-dir для слепого повтора. send_pending может означать уже отправленное
сообщение с неизвестным ID; UUID находится во временном тексте. Ошибки
печатают известный message_id и outcome_unknown.

После успеха запустите scan (output должен отсутствовать):

```bash
./build/tgfs scan \
  --token-file "$HOME/.config/tgfs/secrets/test.token" \
  --storage-chat-id -1003916921678 \
  --service-chat-id -1004400939172 \
  --proxy socks5h://127.0.0.1:10808 \
  --output ./capture-001
```

При снятом pin сохранённый superblock_message_id можно передать scan через
--start-id. Отказы forwardMessage 400 на служебных/несуществующих ID записываются
как пропуски; успешный обход возвращает 0 согласно правилу TGFS-канала.

Локально проверены успех, UUID/ID, существующий pin, нехватка прав,
неизвестный ответ send и отсутствие повторной отправки с тем же intent.
Все 47 тестов и ASan/UBSan проходят (локально detect_leaks=0 из-за ptrace).
Живой init не выполнен: токен хранится у пользователя. Это инициализация
заголовка, а не готовая ФС; удалённое чтение и FUSE остаются следующим этапом.

## Продолжение после явного отказа первой отправки

После подтверждённого отказа sendMessage сохраняется фаза send_rejected и
абсолютный срок send_retry_not_before. Для 429 требуется корректный retry_after.
Когда причина отказа устранена и срок ожидания истёк, повторите исходную
команду init с тем же state-dir, флагом --new-volume и дополнительным
--resume-send. Команда сверит бота, канал, права администратора и отсутствие
закрепа. Она использует сохранённый UUID и перед отправкой записывает новый
send_pending. Если повтор потерял ответ, следующая попытка заблокирована.
Для send_pending с неизвестным ID используйте процедуру ниже.

## Потерянный ответ на первую отправку

Если intent остался в send_pending с superblock_message_id=0, найдите в
канале хранилища сообщение с полным текстом `TGFS_INIT_PENDING <root_object_id>`
из intent.json. Возьмите ID этого сообщения в канале хранилища и запустите
`tgfs init --resume-header --message-id ID` с прежними --storage-chat-id,
--state-dir и настройками подключения, добавив --service-chat-id отдельного
служебного канала.

Команда сверяет исходный канал, ID и точный текст, затем удаляет служебную
копию. После этого она сохраняет проверенный ID и edit_pending, редактирует
исходное сообщение и продолжает закрепление. При новом сбое можно повторить
команду с тем же ID. При отсутствии совпадающего сообщения send_pending
сохраняется и повторная отправка блокируется.

## Продолжение редактирования и закрепления

Для сохранённого edit_pending, pin_ready или pin_rejected запустите
`tgfs init --resume-header` с прежними --storage-chat-id, --state-dir и
настройками подключения, добавив --service-chat-id отдельного приватного
канала. Бот использует forwardMessage для проверки исходного канала, ID и
полного текста. Совпавший временный текст редактируется, готовый SUPERBLOCK
переиспользуется. Служебная копия удаляется перед дальнейшими действиями.
Если удаление не подтвердилось, команда выводит ID копии и останавливается.
После потери ответа на пересылку копия может остаться в служебном канале.

Перед закреплением команда повторно проверяет отсутствие чужого закрепа и
сохраняет pin_pending. Подтверждённый отказ сохраняется как pin_rejected,
при 429 учитывается retry_after. Для pin_pending продолжение возможно,
когда getChat возвращает тот же закреплённый SUPERBLOCK. При отсутствии
совпавшего закрепа исход предыдущей попытки остаётся неопределённым.
Обе команды работают с сохранённым ID и UUID. Используйте тот же бот,
а служебный канал должен разрешать пересылку и удаление служебных копий.

Сверено 2026-11-20. [Bot API forwardMessage](https://core.telegram.org/bots/api#forwardmessage)
и [MessageOriginChannel](https://core.telegram.org/bots/api#messageoriginchannel).

## Завершение после потери ответа на закрепление

Команда `tgfs init --finalize-existing` принимает те же `--storage-chat-id`,
`--token-file` и существующий `--state-dir`. Под локальной блокировкой она
вызывает getChat и сверяет текущий закреп с сохранёнными каналом, ID сообщения,
UUID корня и полным заголовком. Для совпадающего pin_pending фиксируется
complete; завершённое состояние можно проверить повторно. При отсутствии
или несовпадении закрепа команда возвращает ошибку и сохраняет intent.
Отправка, редактирование и закрепление сообщений в этом режиме исключены.

Если сбой оставил полностью записанный intent.tmp, финализация использует его
только при точном совпадении с проверенным результатом. Частичный или чужой
файл сохраняется для разбора.
