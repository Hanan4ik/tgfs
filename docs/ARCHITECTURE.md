# Архитектура — черновик

Статус: proposed. Связанные задачи: [#3](https://github.com/Hanan4ik/tgfs/issues/3), [#7](https://github.com/Hanan4ik/tgfs/issues/7), [#8](https://github.com/Hanan4ik/tgfs/issues/8).

## Компоненты

| Слой | Ответственность |
| --- | --- |
| VFS и FUSE ядра Linux | Обычные системные вызовы приложений и доставка запросов процессу TGFS |
| FUSE adapter | lookup, getattr, readdir, read; позже write, fsync и операции пространства имён |
| Filesystem core | inode, directory entries, версии, локальные дескрипторы и правила видимости |
| Metadata index | SQLite: индекс удалённого каталога; отдельно журнал незавершённых локальных операций |
| Data manager | Staging записи, проверяемый cache частей, SHA-256, random read |
| Commit coordinator | Единственная очередь публикации поколений тома и обработка неоднозначных ответов |
| Transport backend | Upload/download, адресация сообщений, bootstrap, лимиты, retries и capabilities |
| CLI / mount.tgfs | Профили, явная инициализация, mount, диагностика и восстановление |

Писать собственный драйвер ядра не предлагается. FUSE уже соединяет VFS с userspace daemon; выбор языка и обёртки над libfuse остаётся открытым. См. [документацию ядра](https://www.kernel.org/doc/html/latest/filesystems/fuse/fuse.html).

Локальный индекс ускоряет lookup/readdir, но не является единственным местом хранения каталога. Незагруженный staging отличается от cache: его нельзя удалять при очистке кэша. Чистые данные и индекс должны восстанавливаться на другом компьютере из Telegram; неподтверждённая запись может оставаться только на исходном диске.

## Сначала read-only

Первый кандидат MVP: существующий TGFS-том, каталоги и обычные файлы; open/read/getattr/readdir; проверка частей; все изменения возвращают EROFS. Инициализация тестового тома — отдельная административная операция. Обычный mount никогда сам не форматирует канал.

Read-only mount фиксирует одно подтверждённое поколение каталога на время сессии. Автообновление и согласованность с параллельным writer не обещаются; для обновления достаточно remount. Открытый файл привязан к версии, так что его чтение не смешивает старые и новые части.

## Чтение

1. Путь разрешается в directory entry и inode через SQLite.
2. Из подтверждённой версии берётся список частей с диапазонами offset/size.
3. Для нужного диапазона загружаются только пересекающиеся части, при отсутствии проверенного cache.
4. Перед отдачей байт из части проверяются её размер и SHA-256. Для простоты первую реализацию можно заставить скачивать целую часть.
5. SHA-256 всего файла проверяется при полном чтении/явном verify; он не заменяет проверку отдельных частей при random read.

Два read одного chunk должны совместно ожидать одну загрузку. Cache имеет лимит диска и LRU для чистых данных. Cache key включает fs_uuid и неизменяемую идентичность содержимого; путь не подходит в качестве ключа.

## Следующий этап: запись

Предложение: один writer для одного fs_uuid, один хост. Локальный lock привязан к fs_uuid, а не имени профиля. Другой хост этим lock не защищён. Проверка текущего generation перед публикацией обнаруживает часть конфликтов, но не устраняет гонку двух writer; распределённая блокировка без внешнего координатора не заявляется.

| Операция | Предлагаемый контракт, который нужно подтвердить экспериментом |
| --- | --- |
| write | Принимает байты в локальный staging. Успех не означает загрузку в Telegram. |
| read после write на том же mount | Видит staged-версию; другие mount видят опубликованную версию. |
| fsync файла | Ожидает загрузки данных и публикации поколения, содержащего полную версию inode. Ошибка/неизвестный результат не маскируется успехом. |
| flush / close | Может запускать фиксацию и сообщать ошибку там, где FUSE позволяет; явный fsync остаётся точкой подтверждения удалённой фиксации. |
| release | Освобождает ресурсы; не единственный и не надёжный канал сообщения об ошибках записи приложению. |
| rename | Новое пространство имён публикуется одним поколением; читатель не должен видеть промежуточные половины переименования. |
| fsync каталога | Барьер удалённой фиксации изменений соответствующего пространства имён. |
| unlink открытого файла | Имя убирается; открытые дескрипторы держат версию до release. Физическая очистка отдельно. |
| truncate / append / random write | Изменение локального представления, затем загрузка изменившихся частей и нового каталога. |

Commit coordinator сериализует публикации. Общий каталог не должен ссылаться на неготовые версии других открытых файлов. Точная координация dirty inode, rename и fsync(parent) остаётся блокером write-MVP. Не заявлять поддержку сохранения из vim до проверки сценария temp -> fsync -> rename -> fsync(parent).

Первый простой write-вариант может staging-овать целый изменяемый файл. Это требует свободного места, порядка размера файла плюс временные данные; оптимизация по dirty chunks — отдельное решение. Существующие удалённые части неизменяемы, поэтому для изменения содержимого в любом случае создаётся новая версия.

## Сбои и ошибки

- Повреждённый chunk, недостающая подтверждённая часть: EIO; повреждённый cache удалить и один раз получить заново.
- Переполненный staging/cache, когда нет места для необходимой операции: ENOSPC; dirty staging не вытеснять.
- Нет прав канала: EACCES; неизвестный путь: ENOENT; запись в read-only: EROFS.
- Сеть: ограниченный timeout, отмена запросов и документированная errno-политика; offline-чтение только уже проверенных данных. Не возвращать нули вместо отсутствующих байт.
- 429: учитывать retry_after, ограничивать очередь и повторения; не выполнять бесконечный retry внутри системного вызова.
- Timeout публикации: сверить superblock перед следующей записью. При невозможности проверки перейти в состояние recovery required.
- После crash: загрузить опубликованный root, отдельно предложить восстановить локальный dirty staging. Не объявлять неподтверждённые данные удалённо сохранёнными.

## Что пока откладывается

Multiwriter между хостами, NFS export, распределённые locks, writable mmap, POSIX ACL/xattr, device nodes, FIFO/socket, hardlink/symlink и полноценная sparse-семантика — не гарантии первой версии. Формат inode должен позволять добавлять типы. UID/GID/mode сначала можно отображать политикой mount; сохранение реальных Unix-владельцев между машинами требует решения. Telegram-канал не даёт сквозного шифрования; шифрование данных/метаданных и ключи рассматриваются отдельно, если это требование появится.
