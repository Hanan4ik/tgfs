# Сбор журнала Telegram-канала

Реализовано 2026-11-14: `tgfs scan`. Это первый сетевой этап восстановления:
сбор записей и индекс object_id → исходные message_id. Его результат пока
не подключён к ls/cat и FUSE. DIRECTORY/FILE_COMMIT documents и байты CHUNK
на этом этапе не скачиваются; целостность файлов и актуальность каталогов
не считаются проверенными.

## Запуск

Требуется уже существующий SUPERBLOCK из SUPERBLOCK_V1.md, закреплённый в
канале либо указанный через --start-id. Тестовый TGFS_PROBE не является
заголовком; канал с одним probe ещё не инициализирован. Автоматического init
и автоматической подмены закрепа нет.

```bash
./build/tgfs scan \
  --token-file "$HOME/.config/tgfs/secrets/test.token" \
  --storage-chat-id -1003916921678 \
  --service-chat-id -1004400939172 \
  --proxy socks5h://127.0.0.1:10808 \
  --output ./capture-001
```

Каталог назначения должен отсутствовать. При снятом/чужом закреплении
добавьте `--start-id ID_СООБЩЕНИЯ_SUPERBLOCK`. Справка: `tgfs scan --help`.
Токен, timeout и proxy имеют те же ограничения, что у probe.

## Что происходит

1. Создаётся приватный каталог и журнал ID служебных копий.
2. getChat проверяет каналы. Заголовок читается из pinned_message либо через
   forwardMessage по явному locator. Проверяются chat.id, source message_id,
   magic/version/type, start_id, UUIDv4 корня и обязательный next_message.
3. В исходный канал отправляется SCAN_MARKER. Реальный ID ответа B — граница.
   Прототип использует оболочку
   `{"magic":"TGFS","format_version":1,"type":"SCAN_MARKER","next_message":null}`.
   Это экспериментальное кодирование принятого принципа границы.
4. Каждый ID в (start_id, B) запрашивается через forwardMessage. ID копии
   сохраняется отдельно; происхождение сверяется с исходным каналом и ID
   запроса. SUPERBLOCK и собственный маркер уже известны из ответов.
5. TGFS-записи из caption/text сохраняются вместе с document-метаданными
   (включая file_id и file_name); строится object_messages. Проверяется
   оболочка JSON и UUID object_id известных объектных типов. Полная
   семантическая проверка documents/refs относится к следующему этапу.
6. Повторно проверяется доступ к хранилищу. Для известных копий выполняется
   deleteMessage только в служебном канале. Ошибки очистки записываются.
7. journal.tmp записывается/fsync, затем переименовывается в journal.json.
   Временный файл не является завершённым результатом.

Маркеры остаются в канале. Сканер не удаляет исходные сообщения. Попытки
записи/пересылки не повторяются автоматически после неизвестного ответа.
Неизвестный ID копии при потерянном ответе не может попасть в cleanup log;
неизвестные сообщения служебного канала сканер не удаляет.

## Локальные файлы

| Файл/поле | Смысл |
| --- | --- |
| journal.json | Завершённый результат обхода с schema TGFS_JOURNAL_CAPTURE_V1 |
| superblock | Прочитанный заголовок |
| boundary_id | Реальный ID собственного маркера, десятичная строка |
| records | Найденные TGFS-записи: исходный message_id, record JSON, document metadata |
| object_messages | UUID объекта → массив исходных ID его CHUNK/DIRECTORY/FILE_COMMIT |
| unavailable_ids | ID с точным ответом not found / can't be forwarded |
| coverage_verified | Все ID физически доступны; false при ожидаемых пропусках 400 |
| scan_completed / gap_policy | Обход завершён / правило forward_400_is_gap |
| cleanup_pending | Известные ID копий, удаление которых не подтверждено |
| service-copies.log | Все известные ID созданных копий, fsync до дальнейшей обработки |
| cleanup_pending.json | Очередь известных копий после неудачного запуска |

Файлы создаются с 0600, каталог с 0700. Локальная схема — не Telegram
wire-format и не формат snapshot adapter. После аварии service-copies.log
помогает найти копии; некоторые уже могли быть удалены. Автоматического
resume/retry-cleanup пока нет. Неудачный запуск оставляет каталог для
диагностики; для нового запуска нужен другой каталог назначения.

## Ошибки и пределы

- Код 0: обход завершён по принятому правилу forward_400_is_gap; данные файлов ещё не проверены.
- Код 1: сбой; опубликованный journal.json не создаётся при ошибке API/формата.
  Ошибка финального fsync каталога может оставить переименованный файл:
  код возврата всё равно требуется проверять.
- Код 2: неверные аргументы.

Принято пользователем: в TGFS-каналах пересылка разрешена. Поэтому любой
корректный ответ HTTP 400/API 400 от forwardMessage при обходе диапазона
считается несуществующим либо служебным сообщением. Текст ошибки не разбирается.
ID сохраняется в unavailable_ids; scan_completed=true и gap_policy=
forward_400_is_gap обозначают успешное завершение по этому правилу.
coverage_verified остаётся физическим признаком отсутствия недоступных ID;
false при таких пропусках больше не меняет код возврата на 3.
403, 429, timeout, malformed API envelope и ошибки других методов не
превращаются в пропуски. Явный SUPERBLOCK locator также обязан прочитаться:
без заголовка нельзя начать обход. getChat проверяет каналы до/после обхода.

Проход полный, без прыжков по next_message: на чистом индексе ссылка не
доказывает отсутствие записей между её концами. Ссылки не исправляются;
инкрементальные интервалы/checkpoint и ремонт навигации ещё не реализованы.
Изменение captions/documents во время обхода не создаёт атомарного снимка
всех метаданных; маркер ограничивает исходные ID добавленных сообщений.

Максимальный диапазон ID по умолчанию 10000, --max-messages принимает 1..65536.
Лимит проверяется после получения маркера; при превышении маркер остаётся.
JSON результата ограничен 8 MiB; индекс в памяти, непригоден для больших
каналов. Неизвестные типы с корректной TGFS-оболочкой сохраняются как записи,
но не применяются. Публикация DIRECTORY, корень и выбор версии остаются
открытыми: сканер не изобретает правила их применения.

## Проверки

7 сквозных тестов сканера с подслучаями: pin/locator, граница, исходные ID,
посторонний текст, индекс объектов, неполный обход, 429/403, неправильный
origin, malformed envelope, лимит диапазона и очередь очистки. Также проходят
30 тестов ядра, 7 транспорта, ASan/UBSan (локально detect_leaks=0 из-за ptrace).
Живой scan не выполнен: токен остаётся у пользователя, SUPERBLOCK тестового
канала пока не подтверждён.

Следующий этап: получение/проверка DIRECTORY и FILE_COMMIT documents,
определение корня и актуальности каталогов, подключение удалённых частей к
ядру чтения; затем read-only FUSE. Полный #8 этим изменением не закрыт.

Основание: [ADR-0003](decisions/0003-journal-discovery.md).
API сверено 2026-11-14: [getChat](https://core.telegram.org/bots/api#getchat),
[forwardMessage](https://core.telegram.org/bots/api#forwardmessage),
[deleteMessage](https://core.telegram.org/bots/api#deletemessage).

## Результат живой диагностики

На ID 4 после SUPERBLOCK 3 получен отказ `the message can't be forwarded`.
Пользователь подтвердил, что это служебное сообщение закрепления, и принял
трактовку любого forwardMessage 400 как пропуска при разрешённой пересылке.
Сравнение вариантов строк удалено. Сохраняется requested_id и фильтрованная
диагностика остальных ошибок. Повторный scan требует нового output.
