# Чтение файлов из Telegram по сохранённому журналу

Реализовано 2026-11-15: `tgfs read`. Команда соединяет scan, загрузку
DIRECTORY/FILE_COMMIT documents, слияние каталогов и проверяемое чтение CHUNK.
Добавлен постоянный [SQLite-индекс и кэш](PERSISTENT_CACHE.md). FUSE пока отсутствует; создание нового файла в корне доступно через [put](PUT.md).

## Запуск

После `make` используйте журнал уже завершённого scan:

```bash
./build/tgfs read \
  --capture ./capture-004 \
  --token-file "$HOME/.config/tgfs/secrets/test.token" \
  --proxy socks5h://127.0.0.1:10808 \
  ls /
```

Если в канале опубликованы дерево и файл:

```bash
./build/tgfs read \
  --capture ./capture-004 \
  --token-file "$HOME/.config/tgfs/secrets/test.token" \
  --proxy socks5h://127.0.0.1:10808 \
  cat /documents/hello.txt
```

В пользовательском capture-004 были только SCAN_MARKER: `ls /` ожидаемо
выдаст пустой список. Локальный examples/directory-merge не был опубликован
в канал: наличие его файлов на диске не создаёт удалённых имён.

Справка: `tgfs read --help`. Timeout/proxy/direct и файл токена как у probe.
Нужен тот же бот, для которого scan сохранил file_id. Данные ls/cat идут только
в stdout, ошибки в stderr. Коды 0/1/2 — успех/ошибка/неверные аргументы.
Проверяйте код cat: ошибка поздней части или общего хеша может оставить
проверенный префикс в stdout. Для файлов с бинарными данными перенаправляйте
stdout в файл и используйте его только после успешного завершения.

## Последовательность чтения

1. Проверить journal.json: schema, scan_completed, gap_policy, канал, start/B,
   диапазоны, уникальность и возрастание исходных message_id.
2. Проверить getChat для storage_chat_id из журнала. Исходный scan остаётся
   доверенным локальным источником адресации записей; file_id/metadata
   не пересылаются повторно ради подтверждения происхождения.
3. Пропустить SCAN_MARKER. Неизвестный тип записи останавливает импорт.
4. Для DIRECTORY и FILE_COMMIT выполнить getFile/download. Сверить file_id,
   объявленный размер в getFile и фактическую длину с document.file_size из
   scan. Разобрать JSON и проверить семантику существующим ядром.
5. Применить ADD/REMOVE каталогов; конфликты и неполные refs остаются ошибками.
   Корень объявлен SUPERBLOCK и пуст при отсутствии DIRECTORY операций.
6. ls перечисляет entries. Байты CHUNK не скачиваются для ls.
7. cat выбирает канонический FILE_COMMIT, проверяет refs/metadata всех его
   частей, затем вызывает getFile/download только выбранных CHUNK. Проверяются
   размер, SHA-256 каждой части и всего файла. Пустой файл даёт EOF без CHUNK.

Используется исходная граница B из scan. Нового маркера, пересылок, редактирования
сообщений, очистки канала и автоматического init при read нет. Для новых
публикаций нужен следующий scan; в следующем живом опыте свободен capture-005.

## Локальное размещение и границы

Metadata адаптируются к существующему snapshot-ядру в отдельном каталоге
/tmp/tgfs-read-XXXXXX, созданном mkdtemp (0700). Сгенерированные имена файлов
основаны на проверенных исходных ID; имена документов Telegram не используются
как локальные пути. Файлы создаются через openat/O_EXCL/O_NOFOLLOW с 0600.
Временные metadata удаляются при обычном завершении/ошибке. После аварийного
завершения процесса временный каталог может остаться. Секрет токена туда
не записывается. CHUNK скачивается в память и освобождается после проверки.

При холодном кэше метаданные всех объектов загружаются до разрешения пути.
По умолчанию [кэш](PERSISTENT_CACHE.md) сохраняет documents и индекс; при
повторном чтении используются локальные bytes. Без кэша (--no-cache)
сохраняется прежний режим загрузки всех metadata при каждом CLI запуске.

Ограничения: до 65536 записей; JSON capture/адаптера/одного metadata document
до 8 MiB; суммарно metadata documents до 64 MiB. Один CHUNK до 20 MiB.
Сетевой приём имеет собственные ограничения транспорта (в том числе API JSON
до 1 MiB и download до 20 MiB). Требуется document.file_size в capture и
getFile.file_size/file_id в ответе; отсутствие этих полей отвергается.

scan_completed=true/gap_policy=forward_400_is_gap принимаются согласно
условию пользователя о разрешённой пересылке. coverage_verified=false с
unavailable_ids не блокирует read: это ожидаемые пропуски 400. Недоступная
часть/операция, необходимая для чтения, всё равно приводит к ошибке ядра.
Старый capture без этих полей нужно собрать актуальным scan в новом каталоге.

Capture фиксирует captions/границу добавленных ID; getChat при read не
продвигает границу и не выбирает новый root по закрепу. Последующие изменения
метаданных не импортируются автоматически. Это чтение выбранного сохранённого
журнала, не атомарный актуальный mount при конкурентных изменениях.

## Проверки

Добавлены 7 сквозных тестов сетевого чтения с подслучаями: реальный curl на
loopback HTTP double, загрузка metadata и слияние, REMOVE, пустой корень/файл,
ленивые CHUNK, multipart, ранняя/поздняя ошибка SHA-256, неверные file_id/size/path,
JSON, диапазон/повторы записей, незавершённый журнал, канал, отсутствие CHUNK
и 429 без утечки токена. Все запросы read ограничены getChat/getFile/download.
Всего 68 тестов; локальные ASan/UBSan с detect_leaks=0 из-за ptrace прошли.
Пользователь подтвердил живое чтение hello.txt, multipart из трёх частей и пустого файла с кодом 0. Токен хранится у пользователя.

Следующий этап — публикация тестовых данных/операций в канал и живое чтение
непустого дерева, постоянный индекс/cache и read-only FUSE.
