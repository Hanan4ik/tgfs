# Продолжение загрузки до FILE_COMMIT

Реализован явный режим `intent --resume-upload` для прерванного `put`, включая
`--replace`. Сначала остановите исходный writer, сохраните его state-dir и
получите новый завершённый scan. Команда использует исходные object/version/
operation UUID и staging `data.bin`, не перечитывает исходный пользовательский
файл и не начинает новую операцию.

```sh
./build/tgfs intent "${tgfs_net[@]}" \
  --state-dir "$HOME/.local/state/tgfs/put-interrupted-001" \
  --capture ./capture-012 \
  --resume-upload
```

Путь здесь — пример намерения действительно прерванной загрузки. Не меняйте
phase вручную, не удаляйте журнал и не прерывайте рабочую загрузку специально
для этой проверки. Для уже подтверждённого commit команда вернёт
`upload_resume=already_committed`, ничего не отправляя.

## Как принимается решение

1. Обычная диагностика проверяет staging по SHA-256 и части по metadata,
   имени, размеру, SHA-256 и содержимому. Несколько частей одного индекса либо
   ненаблюдённый известный ID блокируют продолжение.
2. Части из capture должны составлять единственный упорядоченный префикс.
   Сохранённые refs должны соответствовать этому же префиксу. Каждая повторно
   используемая часть свежо проверяется через служебную пересылку; копия
   удаляется. Caption должен совпадать с capture и иметь null navigation.
3. Недостающую часть разрешено отправить только если сохранённая фаза и
   recovery-log исключают прежнюю попытку этого индекса либо подтверждают
   отказ конкретной recovery-попытки (правила ниже). `prepared` означает
   отсутствие первых попыток; `chunk_sent` — подтверждённый префикс;
   `chunk_send_pending` включает `pending_part` в уже предпринятые попытки.
   `chunk_response_uncertain` учитывает сохранённый `last_attempted_part`.
4. Перед новой частью записывается и fsync-ится `upload_chunk_pending` с
   индексом в `backlink-repair.log`, затем атомарно сохраняется intent с
   `chunk_send_pending`. Только после этого выполняется sendDocument. После
   подтверждения сохраняются ID и `chunk_sent`.
5. После всех частей сохраняется manifest `commit_document`, ставится
   durable `upload_commit_pending` и фаза `commit_send_pending`, отправляется
   один FILE_COMMIT. Подтверждённый ответ сохраняется в intent; фаза становится
   `backlinks_pending` для create либо `published_backlinks_pending` для replace.

Перед публикациями сверяется закреплённый SUPERBLOCK. Родитель должен иметь
тот же UUID; имя create должно быть свободно в предоставленном capture.
Для replace имя должно указывать на тот же object_id. Более свежая версия
этого объекта не считается конфликтом: проверки base_version как CAS нет.

## Неизвестный исход и старые намерения

Отсутствие сообщения в capture, в том числе forwardMessage 400, не доказывает,
что запрос не был исполнен. Pending из intent или журнала запрещает повтор
ненаблюдённой части. Неподтверждённая HTTP-ошибка также сохраняет барьер; исключение для
новых подтверждённых отказов recovery описано ниже. При потере ответа выполните новый
scan: если часть найдена однозначно, продолжение использует её ID.

У старых `chunk_response_uncertain` без `last_attempted_part` число refs не
всегда позволяет отличить известный ID последней попытки от предыдущего
успеха. Поэтому следующий индекс также консервативно считается предпринятым.
Это может заблокировать реально неотправленную часть; обходить барьер изменением
intent нельзя. Новые writer-намерения сохраняют точный последний индекс.

Фазы после начала FILE_COMMIT без подтверждённого отказа не разрешают
его повторную отправку. При потере
ответа commit ищется новым scan по исходной операции и точному manifest;
затем используются существующие recovery-команды. Если сохранённого manifest
нет, но capture уже содержит commit того же object/version или operation UUID,
новая публикация блокируется для отдельной сверки.

Локальная flock общая с остальными режимами intent. Новый `put` использует тот же lock; другой компьютер и старый writer
он не блокирует. Перед recovery исходный writer должен завершиться. State-dir,
`intent.tmp` и журнал сохраняются при ошибках. Неизвестные служебные копии и
автоматический cleanup журнала пока требуют отдельного решения.

## Что делать после успеха

При `upload_resume=committed` отчёт содержит `uploaded_chunk_ids`, commit ID,
`resumed=true`, `next_step=capture_after_upload_resume`. Массивы verified/missing
описывают входной capture, а uploaded — новые подтверждённые ответы. Команда
не ремонтирует backlinks и не публикует DIRECTORY ADD.

Получите новый scan. Для create выполните [--resume-directory](RESUME_DIRECTORY.md),
после его публикации ещё один scan и [--finalize](FINALIZE_PUT.md). Для replace
после нового scan достаточно `--finalize`. Эти команды проверяют подтверждения
и завершают навигацию и локальное намерение. Уже существующий исторический
commit не означает, что имя сейчас существует в каталоге.


## Подтверждённые отказы CHUNK/FILE_COMMIT (2026-11-18)

Следующий явный запуск `--resume-upload` может повторить запрос, отказ на
который сохранён **предыдущим запуском recovery**. Используются те же правила,
что для [ADD](RESUME_DIRECTORY.md): валидный ok=false, совпадающие HTTP/API
коды 400–499, отсутствие result; для 429 обязательно положительное retry_after.
Внутри одного запуска автоматических повторов и ожидания нет.

Новые upload_chunk_pending/upload_commit_pending содержат operation_id.
После отказа одна fsync-запись upload_chunk_rejected/upload_commit_rejected
содержит тот же UUID, индекс части (либо UUID commit), HTTP/API коды и
retry_not_before. Токен, description и URL в журнал не записываются.
Новый запуск проверяет последовательность и соответствие pending/rejected,
сохранённую фазу и срок. Старые pending без UUID остаются барьером, на их основе
новый rejected не принимается. Повреждённый/чужой/orphan rejected и неоднозначные
попытки блокируются. При ошибке/неполной записи отказа барьер сохраняется.

Для CHUNK повтор разрешён только на сохранённой границе chunk_send_pending:
индекс должен совпасть с pending_part и длиной подтверждённого префикса parts.
Сохранённые известные ID не отменяются отказом. Недостающий известный ID,
повреждённый staging, изменённый pin/source или неоднозначные части блокируют
продолжение. Перед повтором сверяются staging, назначение, все используемые
части и SUPERBLOCK; перед запросом записывается новый pending и intent.

Для FILE_COMMIT требуется commit_send_pending, подтверждённый отказ той же
recovery-попытки, полный сохранённый parts и точный исходный commit_document.
Все части должны присутствовать в capture и пройти свежую проверку.
Пересобранный manifest обязан точно совпасть с сохранённым; замены refs или
UUID нет. При повторе commit части не отправляются. Если до отказа текущая
команда успела отправить части, нужен новый scan с этими частями; одного
повтора на старом capture будет недостаточно.

Новый pending заменяет разрешение старого rejected. Если повтор потеряет ответ
либо получит 5xx/некорректный успешный Message, ещё один слепой повтор запрещён.
После нового scan найденные CHUNK используются без переотправки, а найденный
commit даёт already_committed. Отсутствие сообщения само по себе не снимает
барьер. Cooldown использует системные часы; их корректность обязательна.

В PR #41 исходный `put` ещё не записывал такие evidence; начиная со следующего
этапа он использует этот же протокол (ниже). Старые uncertain intents без
подтверждённого отказа, init/unlink и автоматический cleanup сохраняют ограничения. Не редактируйте фазу или журнал
для обхода проверки. Отказы/продолжение проверены тестовым API; специально
провоцировать сбои в живом канале не требуется.


## Отказ при первоначальном put (2026-11-20)

Новый `put` (включая `--replace`) создаёт приватный backlink-repair.log и
берёт ту же неблокирующую flock, что изменяющие режимы intent. Создание журнала
закрепляется fsync каталога до первой публикации. Lock удерживается до выхода
из put; попытка recovery того же state-dir во время writer отвергается.
Это локальная блокировка, не координация разных компьютеров/копий intent.

Перед каждой CHUNK и FILE_COMMIT writer fsync-сохраняет pending с UUID
операции и индексом/commit, затем атомарно сохраняет pending-фазу intent.
Подтверждённый отказ 4xx сохраняется тем же rejected-протоколом, что у recovery.
Writer возвращает ошибку и сохраняет chunk_send_pending/pending_part либо
commit_send_pending с полным manifest; автоматически запрос не повторяется.
После исправления причины отказа и истечения cooldown можно получить новый
scan и вызвать `intent --resume-upload` с тем же state-dir.

Неизвестный ответ, 5xx, некорректный Message и неподдержанный отказ сохраняют
прежние uncertain-фазы и pending-барьер. Если сохранение rejected не удалось
или процесс оборвался во время append, запись не разрешает повтор. Старые
намерения без rejected не меняются задним числом; ручной обход запрещён.

Успешные CHUNK/commit, байты и UUID публикуются по прежнему протоколу.
ADD первоначального put, mkdir/unlink/init и очистка журнала в этот этап
не входят. Живой непустой recovery пока проверен тестовым API; специально
провоцировать отказ в Telegram не нужно.
